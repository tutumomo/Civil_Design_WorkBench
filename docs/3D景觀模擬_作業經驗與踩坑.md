# 手繪景觀圖 → 3D 意象模擬：作業經驗與踩坑

- **適用**：使用者丟一張手繪／示意圖（避車彎、欄杆、步道、擋土牆、涼亭…），要求「做成 3D 景觀模擬圖／實景意象圖」。
- **定位**：**意象模擬（concept render）**，不是施工圖、不是實景照片、不是測量成果。對外交付一律明寫。
- **首次落地**：2026-11-06「路旁避車彎」案（三次返工後定案）。
- **參考實作**：`tools\landscape3d\bay_scene.py`（444 物件／37,593 面，可直接重跑）＋`tools\landscape3d\plan_view.py`（正交俯視補圖）。
- **踩坑濃縮版**：`docs\踩坑紀錄.md` §AG。

---

## 0. 一句話結論

**三次返工全部來自「我把圖看錯」，沒有一件是工具或渲染參數的問題。**

| | 成本 |
|---|---|
| 開工前送一張判讀確認表 | 使用者回一句話（30 秒） |
| 看錯一次 | 一輪建模＋3 張渲染（約 171 s 機時）＋整份交付清單重寫＋信任折損 |

所以：**先判讀、再建模。判讀不確認，不要開始拉幾何。**

## 1. 判讀先行（READ BEFORE BUILD）

### 1.1 三次返工實錄

| 輪次 | 我做的 | 原圖實際是 | 誰發現 | 拆掉的東西 |
|---|---|---|---|---|
| 1 | 路邊**平行停車格**（5.0×2.5 m，畫白線格位） | **避車彎**：車道邊線局部外凸的避讓空間 | 使用者：「有一個重點，路旁避車彎，你沒有注意到」 | 格線、整組平面定位 |
| 2 | 避車彎＋**0.95 m 擋土牆**（壓梁、7 道伸縮縫、排水孔） | **路緣石 0.20×0.20 m** | 使用者：「旁路應該是路緣石（高度約20cm），不是擋土牆」 | 牆體、壓梁、伸縮縫、排水孔；坡趾高程 0.95 → 0.12 m |
| 3 | 緣石＋1.00 m 綠帶＋坡趾起坡 | 定案 | — | — |

兩次糾正**都落在「構造物定名」**，不是尺寸、不是比例、不是材質。
→ 判讀時最該問的是「**這是什麼東西**」，不是「它多大」。

### 1.2 開工前必送的「判讀確認表」

列 5~7 列，每列都要寫「若判錯的後果」，讓使用者一眼看出哪一列最貴：

| 圖上看到 | 我的解讀 | 數值 | 依據 | 若判錯的後果 |
|---|---|---|---|---|
| 車道邊線局部外凸 | 避車彎（不是停車格） | 加寬 3.20 m | 邊線外凸、無格線 | 平面幾何全錯 |
| 路側窄長條 | 路緣石（不是擋土牆） | 0.20×0.20 m | 無壓梁、無排水孔 | 多一批牆體構件＋坡趾高程錯 |
| 「1.2M」 | 緣石背至坡趾淨寬 | 0.20＋1.00 | 無引出線 | 停車空間深度錯 |

規則：
- 只問「**我這樣讀對不對**」，不要在確認表裡問「要不要做 A 還是 B」（那是設計決策，會拖住進度）。
- 使用者回「對」就開工；回一個詞（例如「避車彎」）就照那個詞整組重做。
- **不要在回覆裡只用一句話帶過判讀**——寫成表格，使用者才驗得動。

### 1.3 避車彎 vs 平行停車格

| 特徵 | 避車彎 | 平行停車格 |
|---|---|---|
| 車道邊線 | **局部外凸**（凹入路側空間） | 平直 |
| 幾何主角 | 進出**漸變段**（S 曲線）＋緣石繞行 | 格線（白線）與格位尺寸 |
| 標線 | 通常無格線、無編號 | 成排格線，常有編號 |
| 緣石 | 隨外凸邊線**連續繞行**整個彎 | 沿路直線 |
| 用途 | 臨時避讓／短暫停等 | 停放 |

判別的關鍵一句：**「車道邊線有沒有轉折外凸？」** 有＝避車彎。
判錯的代價不是換個材質，而是**整個平面拓撲不同**，無法局部修補。

### 1.4 路緣石 vs 擋土牆（本案最貴的一課）

| 特徵 | 路緣石 | 擋土牆 |
|---|---|---|
| 高度 | 15~25 cm（本案 20 cm） | 常 ≥60 cm，本案誤設 95 cm |
| 頂面 | 倒角／圓角收邊 | 壓梁、常有點狀欄杆基座 |
| 分縫 | 每 2~4 m 一道細縫 | 伸縮縫 10~20 m＋填縫板 |
| 排水 | 無 | 排水孔（PVC 管／洩水孔） |
| 與坡的關係 | 坡在它**背後自己爬升**（坡趾可低於緣石頂） | 牆**擋**土，牆背填土**到牆頂** |
| 坡趾高程 | ≈ 緣石高（本案 0.12 m） | ＝牆頂（本案誤設 0.95 m） |
| 圖面畫法 | 窄長條、單線＋一條厚度線 | 有厚度剖面、背後土紋／斜線 |

**一句話判別：「它擋不擋土？」** 坡背後自己爬升＝緣石；牆背填土到頂＝牆。

代價不只是物件數：牆會把**坡趾高程**從 0.12 抬到 0.95，坡面網格、植栽散佈高度、相機視點、涼亭相對高度**全部要重算**。這是本案返工第二輪的真正成本。

### 1.5 沒有引出線的數字＝至少三種讀法

「1.2M」的可能讀法：① 帶寬 ② 淨距 ③ 停車深度。

處理順序：
1. 並列候選讀法；
2. 用**合理性**砍掉不可能的（停車格深 1.2 m → 車停不進去 → 刪）；
3. 剩下仍 ≥2 種 → 交付清單「判讀假設」明列，回覆用一句話請使用者確認；
4. **絕不靜默選一個**（AGENTS.md 協作紅線：圖面標註有歧義時並列解讀與後果）。

### 1.6 使用者的一句話＝最高價值資訊

使用者不會逐項驗收圖面，他只會在看到「明顯不是他畫的東西」時回一句。
→ 判讀階段主動去找「**使用者最可能糾正的那一點**」，先問掉；不要等他講第二次。
本案兩次糾正都發生在**同一個層級（構造物定名）**，第二次本來可以靠第一次的教訓事先問出來。

## 2. 執行環境（Blender MSIX）

### 2.1 一律經 `blender_runner.py`，不直接呼叫 `blender.exe`

- Blender 是 **MSIX（Microsoft Store）5.2.3**，exe 在 `C:\Program Files\WindowsApps\BlenderFoundation.Blender_5.2.3.0_x64__...\Blender\blender.exe`。
- 掃 PATH 或 `C:\Program Files\Blender Foundation` 會**誤報「未安裝」**。
- `tools\blender\blender_runner.py` 用 `Get-AppxPackage` 解析實際路徑，再以 `Invoke-CommandInDesktopPackage` 啟動（桌面封裝程式無法直接 spawn）。

#### ⚠ 腳本裡的 `__file__` 是「複本」的路徑

runner 會把腳本複製成 `_temp\blender\<ts>_<腳本名>\user_script.py` 再 `exec`，並把 cwd 設在該 job 目錄。
所以**任何用 `__file__` 算出來的路徑都是 job 目錄起算**，不是 `tools\` 或 `_temp\landscape3d\`：

- `os.path.dirname(os.path.abspath(__file__))` → `...\_temp\blender\<job>`
- 固定層數的 `parents[1]`／`dirname` 連續三次 → 幾乎必錯（曾出現 `ModuleNotFoundError: No module named 'project_paths'`，但從未被當成錯誤來源，因為**在 `_temp` 時期這段是寫死絕對路徑**，提升到 `tools\` 改成 `import project_paths` 才爆出來）。

**正確寫法**（`tools\landscape3d\bay_scene.py` 已實作 `_find_tools_dir()`）：由 `__file__` 與 `cwd` 各向上最多 6 層，逐層試 `r` 與 `r\tools` 有沒有 `project_paths.py`，並先看 `CIVIL_AI_ROOT`；找不到才退回相對路徑。**不要數層數、不要寫死磁碟機代號。**

### 2.2 指令與 timeout

```powershell
python tools\blender\blender_runner.py run "tools\landscape3d\bay_scene.py" --timeout 1200
python tools\blender\blender_runner.py run "tools\landscape3d\plan_view.py" --blend "out\路旁避車彎_3D\路旁避車彎_3D場景.blend" --timeout 600

# 參數覆寫（驗證／預覽）：一律用 --arg，不要用 $env:
python tools\blender\blender_runner.py run "tools\landscape3d\bay_scene.py" `
  --arg "BAY_OUT=D:\Civil_Design_WorkBench\_temp\landscape3d\verify_out" `
  --arg "BAY_PREVIEW=1" --timeout 600
```

- **timeout 給 1200，不要給 300**：MSIX 啟動＋建模＋多張渲染會超過 300 s。
- **`$env:` 傳不進 Blender，`--arg KEY=VALUE` 才進得去**：MSIX 版由 `Invoke-CommandInDesktopPackage` 開**新行程**，呼叫端的環境變數不會被繼承。實測 `$env:BAY_OUT` 指到 `_temp` 仍照樣寫進 `out\`（把已交付的檔覆寫掉），`$env:BAY_PREVIEW=1` 完全沒作用、照樣跑滿 3 張。`blender_runner.py` 已加**可重複**的 `--arg`，`bay_scene.py` 的 `_opt()` 先讀注入的 `ARGS` 再讀 env（舊寫法留著不影響，但不要再用）。
- 回傳 JSON 含 `ok`／`elapsed_s`／`artifacts`／`result`／`log_tail`；**失敗先看 `log_tail` 與 traceback**。

### 2.3 job 目錄與機讀結果

- 每次執行落在 `_temp\blender\<YYYYMMDD_HHMMSS>_<腳本名>\`，內含 `user_script.py`、`blender.log`、`result.json`。
- 腳本要讓結果**機讀**，必須在**模組層**設 `RESULT = {...}` 與 `ARTIFACTS.append(...)`。
  - 反例：`plan_view.py` 原本只 `print("RESULT:", ...)` → runner 的 `result` 欄位是 `null`，只能翻 log 才知道數值。
- 實測 job 紀錄可當「機時帳」：

| job | 內容 | elapsed |
|---|---|---|
| `20261106_130054_bay_scene` | 建模＋存 .blend＋4 張 1600×900 | **135.7 s** |
| `20261106_130340_plan_view` | 載入 .blend＋正交相機＋1 張 | **38.7 s** |
| `20261105_144657_build_scene` | 路徑寫錯（`_temp\landscape3d` 不存在） | **0.01 s 失敗** |
| `20261106_131643_bay_scene` | 提升到 `tools\` 後首跑失敗（`__file__` 指到複本） | **0.02 s 失敗** |
| `20261106_131739_bay_scene` | 修好後完整重跑（建模＋3 張 1600×900）；主視角 **1,547,599 bytes，與前一版完全相同** → `random.seed` 下可重現 | **171.3 s** |
| `20261106_132152_bay_scene` | `--arg` 覆寫驗證（1 張 1280×720、32 samples、寫 `_temp`） | **10.3 s** |

> 預覽模式只要 **10.3 s，約完整出的 1/17**。**驗證一律先跑預覽、寫 `_temp`**，別拿正式產出去試錯。

> 0.01 s 失敗是好事：**路徑類錯誤會立刻回報**；會拖到 timeout 的是「Blender 起來了但卡住」（例如渲染設定過重、場景過大）。

### 2.4 `--blend` 模式的硬規則

1. 腳本**不得**呼叫 `bpy.ops.wm.read_factory_settings()`，否則載入的場景被清空，還會**照樣渲染出圖、不報錯**（最惡毒的一種靜默失敗）。`plan_view.py` 已加「物件數為 0 就 raise」的防呆。
2. 取物件用 `bpy.data.objects.get(...)`，取不到就 `raise`；不要相信 `scene.camera` 的既有值（可能是舊相機）。
3. 重跑前先刪同名物件／相機，否則 `CAM_俯視平面.001` 會一直累積。

## 3. 建模手法：讓「改一個數字」變成可行

### 3.1 版面常數集中成一個區塊

`bay_scene.py` 的「版面常數」區塊（用 `grep -n "BAY_DEPTH =" tools\landscape3d\bay_scene.py` 定位；**不要寫行號**，改幾行就失準）：

```python
Y_LANE_FRONT = -4.50          # 車道外側邊線
LANE_W = 4.50                 # 主線車道淨寬（貫通不中斷）
BAY_DEPTH = 3.20              # 避車彎向坡側加寬深度
BAY_X0, BAY_X1 = 2.00, 7.00   # 全深段 5.0 m
TAPER = 5.00                  # 前後漸變段各 5.0 m
CURB_W, CURB_H = 0.20, 0.20   # 路緣石（路側唯一混凝土構造）
VERGE_W = 1.00                # 綠帶（緣石背至坡趾）
TOE_Z = 0.12                  # 坡趾高程
SLOPE_W, Z_TOP = 9.50, 5.30
CAR_X, CAR_Y = 4.50, 1.62
```

**原則**：所有「使用者可能會改」的數字都在這裡，其他程式碼不得出現裸數字。
使用者說「加寬改成 2.5 m」時，只改 `BAY_DEPTH` 一行、重跑。

### 3.2 幾何函式化，不要各畫各的

| 函式 | 作用 |
|---|---|
| `bay_edge(x)` | 該里程的避車彎外凸深度（含 smoothstep 漸變） |
| `toe_y(x)` | 坡趾位置 ＝ `bay_edge(x) + CURB_W + VERGE_W` |
| `slope_z(y, x)` | 坡面高程（坡趾→坡頂線性） |
| `band(...)` / `sweep(...)` | 沿曲線掃出帶狀構造（緣石、標線、綠帶） |

好處：**緣石、綠帶、坡面、緣石繞行、標線全部吃同一組函式** → 改 `BAY_DEPTH` 一處，五個地方同步；
反過來若各處自己算，改一個參數就會「緣石和坡趾對不上」，而這種錯在透視圖上**看不出來**。

### 3.3 漸變段用 smoothstep，不要用直線

直線漸變會在「漸變↔全深」交界出現折角，`sweep` 掃出來的緣石會**自交翻面**。
`smoothstep` 讓曲率連續，S 形進出也才像實際道路。

### 3.4 用程式反證，不靠目視

車輛包絡 vs 緣石：算車輛 4 個角點到 `bay_edge(x)` 的距離，確認全在緣石內側（本案車身 y = 0.72~2.52，緣石在 3.20 之外）。
「看起來沒壓到」不算證據——**渲染圖上 5 cm 的差距看不出來**。

### 3.5 共用件庫

`box()`、`cyl()`、`blob()`（不規則量體／灌木）、`grid_mesh()`（地形）、`make_cam()`、`pavilion()`、`suv()`。
新案沿用同一組件庫＋材質，整本簡報的視覺調性才會一致（這是使用者會直接感受到的品質差異）。

## 4. 渲染設定與時間預算

| 設定 | 定案值 | 備註 |
|---|---|---|
| 引擎 | Cycles，**CPU** | MSIX 版 GPU 不一定可用，CPU 較穩 |
| 解析度 | 1600×900、PNG / RGB / 8-bit | 簡報與聊天預覽都夠 |
| samples | 110（預覽 64） | 配合 adaptive sampling |
| adaptive_threshold | 0.015（預覽 0.02） | |
| time_limit | 260 s／張（預覽 150 s） | 單張上限，防單張拖垮整批 |
| 降噪 | `use_denoising = True` | 低 samples 就可用 |
| max_bounces / diffuse / glossy | 4 / 2 / 2 | 戶外場景不需要更多 |
| 色彩管理 | AgX、exposure **−1.15**、look `AgX - Punchy` | look 名稱跨版本會變 → 用候選清單 fallback |
| `use_persistent_data` | **True** | 同場景多視角必開，省下每張重建 BVH |

**時間實測**（1600×900、Cycles CPU）：建模＋存 .blend＋4 張＝**135.7 s**；純載入 .blend＋1 張正交俯視＝**38.7 s**。
→ 使用者要「再改一個數字重出」，成本約 **2.5 分鐘**，這是可以即時往返的量級。

> `time_limit` 是早停機制：**兩次同設定渲染的像素不會完全相同**。對帳用「解析度＋檔案大小＋肉眼」，不要用像素雜湊。
> 色彩管理的 look 名稱（`AgX - Punchy`）在不同 Blender 版本可能改名 → 用 candidate 清單逐一 try，並把實際採用的值印出來。

## 5. 自檢與交付

### 5.1 用 RESULT 量測值反證常數

`bay_scene.py` 的 `RESULT` 會回傳 `bay_edge(5.0)=3.20`、`toe_y(5.0)=4.40`、`curb_h_m=0.2`、物件數、面數。
交付前逐項對一次「這是不是我要的」——**這是唯一能證明「改到對的地方」的證據**（渲染圖不能）。

### 5.2 正交俯視圖是第二證據

透視圖看不出「車道邊線有沒有外凸」「緣石有沒有繞對」。
**多花 39 s 出一張正交俯視圖**，一眼就能被使用者驗證，也能自己抓錯。本案第 2→3 輪就是靠它確認幾何。

### 5.3 冪等重跑

- 相機、物件先刪同名再建。
- `.blend` 直接覆寫。
- `BAY_PREVIEW=1` 只出第一張並加 `PREVIEW_` 前綴（調參時省時間）。

### 5.4 交付夾衛生（`out\` 只放交付檔）

- **`bpy.ops.wm.save_as_mainfile()` 會產生 `.blend1` 備份**（本案 813,452 bytes），直接躺在 `out\` 裡。
  → 存檔前 `bpy.context.preferences.filepaths.save_version = 0`（`tools\landscape3d\bay_scene.py` 已加），或事後搬到 `_temp\`。
- 舊版目錄（`out\路旁停車_3D\` 之類）**作廢要經使用者同意才刪**；作廢期間不要列入交付清單。
- 原圖參考檔不小心複製進 `out\` 的要搬走。

### 5.5 交付清單必含六項

1. **性質聲明**（景觀意象模擬，非施工圖／非實景照片）
2. **尺寸對照表**（圖上數值 ↔ 模型數值）
3. **判讀假設與待確認項**（每個沒把握的數字寫清楚）
4. **重跑指令**（貼上就能跑）
5. **限制清單**（地形未測量、車輛植栽為示意模型、未計日照方位…）
6. **自評可信度**（1~10，並寫出扣分理由）

## 6. 踩坑總表

| # | 症狀 | 真正原因 | 對策 |
|---|---|---|---|
