# 全案回歸測試（`tools/selftest/regression.py`）

> 2026-10-28 建立｜工具改一次就得手動跑全案全軸，靠人記得跑，遲早漏掉 ——
> 而漏掉的那一次，通常正好是改壞的那一次。

## 1. 一條指令

```bat
python tools/selftest/regression.py                      :: 比對基準（全部案件）
python tools/selftest/regression.py --list               :: 列出會被掃到的案件
python tools/selftest/regression.py --only 排水溝U型      :: 只跑指定案件
python tools/selftest/regression.py --only 排水溝U型,箱涵三孔測試
python tools/selftest/regression.py --update             :: 重寫基準（改了設計才用）
python tools/selftest/regression.py --update --only 排水溝U型
```

- 逐案跑 `case_package.py`（含出圖、預算、報告、三道對帳閘門）
- 收集關鍵數值，與 `tools\selftest\baseline.json` 比對
- 任一項不符 → 退出碼 1，列出「基準 → 現在」
- `--only` 可重複給，也可逗號分隔；案名不存在時退出碼 2。`--only` 只比對指定的案件，未跑的案件不會被列為「案件已不存在」。
- `--update --only X` 只改寫 X 的基準段落，其他案件原樣保留；不加 `--only` 則整份重寫。

> 回歸只證明「既有案件沒被改壞」。**新增或修改設計計算器**另有一道上架檢核
> （八關：引擎／目錄／範例／輸出形狀／條文／下拉／主題卡／標籤）：
>
> ```bat
> python tools/selftest/design_launch_check.py <id>
> ```
>
> 兩者不可互相取代；流程見 `docs\設計計算器上架SOP.md`。

## 1.1 統一入口與 CI

`tools/selftest/run_all.py` 是全部自測的唯一入口（回歸只是其中一支），CI 也用它：

```bat
python tools/selftest/run_all.py                  :: 全部（含回歸，需本機 CAD）
python tools/selftest/run_all.py --changed        :: 只跑與 git 改動相關的
python tools/selftest/run_all.py --no-cad         :: 跳過回歸（無 CAD 後端時）
python tools/selftest/run_all.py --skip regs-verified
python tools/selftest/run_all.py --list
```

| id | 內容 | 需要 |
|---|---|---|
| `design-core` | 設計引擎手算對照（unittest，158 項） | — |
| `design-workbench` | 設計工作台 API／目錄規則 | — |
| `design-launch` | 計算器上架檢核 G0~G8（全部） | — |
| `regq` | 規範查詢引擎與主題卡 | — |
| `regs-verified` | 已驗證公式／圖表庫 | — （**目前有已知缺口，見 §6**） |
| `boq-rules` | 預算費率核心（對真實預算書） | — |
| `portable-paths` | 沒有寫死的 Windows 絕對路徑（排除 `docs/已驗證環境快照.md`） | — |
| `regression` | 全案回歸 | 本機 CAD 後端、既有 `out/` |
| `ocss-checks` | OCSS 交叉驗算 | OCSS 桌面程式（`--with-ocss` 才跑） |

- `--changed` 依 `git diff HEAD` 與未追蹤檔挑選；**任何 `tools/` 改動都會命中 `regression`**，這是照 `AGENTS.md` §3。
- CI：`.github/workflows/selftest.yml`（push／PR 觸發）跑 `run_all.py --no-cad --skip regs-verified`；全案回歸不在 CI，交付前仍須在本機跑。
- 不在 CI 的兩項：`regression`（需 CAD 後端與產物）、`ocss-checks`（需桌面程式）。

## 2. 基準內容（11 案）

| 案件 | 模型 | 納入的關鍵數值 |

| 擋土牆3m重力式 | wall | 斷面淨面積 3.375／**滑動 FS 1.500／傾倒 3.860／承載 13.542**／檢核全過 |

## 3. 負面測試（證明它會擋）

把基準的「滑動FS」改成 9.999、「通水容量」改成 0.1：

```
✗ 與基準不符 2 項：
   · 排水溝U型／通水容量：0.1 → 0.544
   · 擋土牆3m懸臂式／滑動FS：9.999 → 2.379
exit=1
```

還原基準後回到「✓ 基準全部相符（6 案）」。

## 4. 建立的過程中抓到的問題

### 4.1 `analyse()` 沒有扁平的 `FS_sliding` 鍵

`retaining_wall.analyse()` 回傳的是 `checks: [{item, value, limit, ok}]`，
沒有 `FS_sliding` / `FS_overturning`。第一版回歸直接讀 `r["FS_sliding"]` → `KeyError`
→ 整段設計數值被 `except` 吞掉，基準裡只剩斷面積。

**例外處理寫成 `except: pass` 會讓「沒抓到」看起來像「沒問題」。**

### 4.2 合力作用點卡在邊界（真實 bug）

抓 FS 時一併看到 `合力作用點（土層基礎，1/3 中段）` 是 **False**：

```
x_lo = 1.95 × (0.5 − 1/6) = 0.649999…
x_R  = 0.6499            → 判不合格（差 0.0001 m）
```

這是**邊界值 + 浮點誤差**，不是真的偏心。已加 0.05% BL 容差。

> 更值得注意的是：**這條檢核沒有任何交付閘門在管**。
> `check_delivery` 管圖面、`dxf_takeoff` 管圖數一致、配筋閘門管鋼筋排法 ——
> 但「設計檢核有沒有全部通過」一直只靠報告上印出來的那張表，沒有人擋。
> 這是下一個該補的閘門。

## 5. 什麼時候該跑

| 時機 | 為什麼 |
|---|---|
| 改 `tools/design/*` 任一計算模組 | 數字會變，要確認是「有意的變」 |
| 改 `qty_models` / `case_core` | 數量與派生會變 |
| 改繪圖模組 / `chapters.json` | 圖與報告會變 |
| 交付前 | 最後一次確認六案都還在基準上 |

**改了設計（斷面、流量、鋼筋）才用 `--update`**；只是重構程式不該改基準。

## 6. 已知缺口

- `regs-verified` 的 `barrier108_ramp_slope` 指向《建築物無障礙設施設計規範》，該規範的 PDF 與全文已在 `data/法規/`，但**尚未登錄 manifest、也未進索引**；`build_index.py` 目前沒有對應的 barrier 切分器。修好之前，`run_all.py` 會在預設執行中如實回報失敗（CI 以 `--skip regs-verified` 排除並另步顯示）。
- 處理方式見 `docs/建築物無障礙設施設計規範_取得與條文庫.md` §4（`barrier_units()` 與三種 PDF 斷行陷阱）。
