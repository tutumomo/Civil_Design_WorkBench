# 對話上下文預算（圖片是會累積的炸彈）

> 建立：2026-11-02。事故：2026-11-01 22:08 規範入庫主對話連續多輪成功後，突然每送一次就 `413 Failed to buffer the request body: length limit exceeded`，整條產線停住。
> 適用：任何「要用視覺模型讀原頁圖」的長流程（B 類轉錄、圖表核對、掃描件比對）。

## 1. 事故原因（已量化，不是推測）

| 事實 | 數值 | 來源 |
|---|---|---|
| 該對話累積的圖片 | **211 張** | `pi-agent-home\sessions\2026-10-30T10-45-38-890Z_…jsonl` |
| 圖片 base64 總量 | **48.17 MB** | 同上 |
| 文字量 | 2.93 MB | 同上 |
| 每輪實際送出的 body | **約 51 MB**（整段歷史全部重貼） | 同上 |
| 最後一張圖的時間 | 22:08:35（= 413 前 1 秒） | 同上＋`logs\agent-2026-11-01.ndjson` |

**機制**：對話歷史不會只送「新增的部分」，每次請求都重貼整段歷史；圖片一旦進了 context 就永久跟著，除非對話被壓縮或換掉。所以圖會**單調累積**：
第 1 張 → 0.2 MB，第 100 張 → 23 MB，第 211 張 → 48 MB，然後撞上游的 body 上限（413）。

## 2. 為什麼自動壓縮沒有救到（關鍵盲點）

- 自動壓縮的觸發條件是 **token 數**，不是 **位元組數**。
- 該模型 context 1,048,576 tokens、`compaction.reserveTokens` 100,000 → 要 **約 948k tokens** 才會觸發壓縮。
- 211 張圖大約只佔 **30 萬 tokens 上下**（圖片的 token 遠低於它的 base64 位元組），所以永遠達不到門檻 → 壓縮永遠不啟動 → 位元組卻已經爆了。

**結論：只要流程是「一張一張讀原頁圖」，就一定要自己管圖片張數，不能等系統壓縮。**

同樣的累積也解釋了 20:41 那次 `MiniMax: the num of image is larger than the limit: 200`——那是**張數**先撞牆，413 是**位元組**撞牆，同一個病因。

## 3. 三條硬規則（照做就不會再卡）

### 規則 1：讀原頁圖一律交給子代理，主對話只收文字

已實測：主對話叫子代理讀 `TOMO_style_test.png`，子代理回一句話描述；事後檢查主對話 session 檔，**image block = 0**。圖只存在子代理自己的 context，子代理結束就跟著消失。

用法（在主對話直接說）：

```
派一個 scout 子代理：讀 D:\公司案件.AI\_temp\regs_pages\look\rc112_p398.png，
只回傳「條號、表號、三列公式、以及你確定的下標」純文字，不要貼圖、不要寫檔。
```

轉錄結果由子代理回文字 → 主對話再寫進 `tools\regs\verified\*.json`。
**主對話從頭到尾不需要看到圖。**

### 規則 2：每批 20 條就換一次對話

單一對話的圖片預算：**40 張以內（約 10 MB）**。
20 條 × 每條 1~2 張 ≈ 20~40 張，剛好在安全區。

換對話時貼上第 4 節的交接 prompt，30 秒就能接上（本專案所有狀態都在檔案裡，不在對話裡）。

### 規則 3：開工前先量預算

```bat
python -E -P -X utf8 tools\regs\ctx_budget.py
```

- `OK`：繼續做
- `WARN`（≥10 MB 或 >120 張）：這批做完就換對話
- `OVER`（≥25 MB）：先換對話再開工
- `FATAL`（≥40 MB 或 >200 張）：**已經送不出去了**，只能換對話

給閘門用：`ctx_budget.py --gate 25` 有任何 session 超過 25 MB 就 exit 1。
（旁註：事故對話現在是 `FATAL 211 張 51.10 MB`。）

## 5. 如果一定要留在原對話繼續

只剩兩個辦法，都不是萬靈丹：

1. 在該對話輸入 `/compact`：把舊訊息換成摘要，舊圖才不會再送。**風險**：Cindy 目前的執行紀錄裡從未出現過壓縮事件，`/compact` 是否被轉送到引擎未經驗證——試一次，若沒反應就別再試，直接換對話。
2. 別再往上加圖：也就是後續用「純文字」操作（查索引、改 JSON、跑閘門），要讀新頁面時才派子代理。這樣 body 不會再長大，但已經 51 MB 的歷史仍可能讓下一次請求失敗。

**建議直接換對話**（規則 2），成本 30 秒，成功率 100%。

## 6. 這件事算不算 Cindy 的問題？

算，屬於「健壯性缺口」，可以回報 issue。三個具體點：

1. **壓縮門檻只看 token，不看 body 位元組**：1M context 的模型＋圖片累積，會先撞位元組上限，而自動壓縮永遠不觸發（本案例 211 張圖只約 30 萬 tokens）。
2. **沒有事前防護**：MiniMax 已明確回「圖片上限 200」，413 也是硬擋；但送出前沒有任何「張數／位元組」預檢或提示（pi 文件自己也寫 `images.maxPerRequest` 之類「does not yet rewrite or reject history」）。
3. **錯誤訊息不可行動**：畫面只顯示 `413 Failed to buffer the request body: length limit exceeded`，沒說「是圖片太多、請換對話或壓縮」。

建議的 issue 標題：
`Long image-heavy sessions hit 413 body limit while auto-compaction (token-based) never triggers`
