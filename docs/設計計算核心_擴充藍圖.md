# 設計計算核心擴充藍圖（擋土牆／箱涵／排水／滯洪／建築構架）

> 建立日期：2026-10-29
>
> 目的：把未來常用工項納入同一套可追溯、可回歸、可接到圖面／數量／預算／報告的設計核心，
> 避免每一種工項各寫一支互不相容的計算腳本。

## 1. 結論

這五類需求應共用「幾何、載重、結構分析、水理、構材設計、規範引用」等底層模組，
上層才分成擋土牆、箱涵、排水系統、滯洪池與建築構架等產品介面。

建議不要新增五支獨立的大型腳本。應維持下列分層：

1. **輸入層**：案件 JSON、單位檢查、材料與地質參數。
2. **共同引擎層**：土壓力、平面構架、RC 構材、基礎、水文、水理。
3. **工項模型層**：擋土牆、箱涵、排水網路、滯洪池、建築樑柱基礎。
4. **交付層**：數量、斷面圖、配筋圖、預算、報告與圖數對帳。
5. **查詢層**：規範主題卡、條文全文、計算工具與案例互相連結。

目前規範查詢台已有 34 部法規、13,068 條索引，且「擋土牆、箱涵、排水溝、滯洪池、
淺基礎與承載力」已有主題卡。下一階段不是重做查詢台，而是把每張主題卡連到可執行的
計算引擎與案例。

**2026-10-29 已落地**：20 個計算器（含疊砌式 `block_wall`、扶壁式 `counterfort_wall`、加勁式 `mse_wall`、錨定式 `anchored_wall`、渠道水面線 `channel_profile`）已接到 `design_api.py`（`civil-design-run/1`）、
`design_cli.py`、MCP 與 `/design` 網頁工作台。下列表格保留為能力邊界；沒列在
「目前已有」的項目就是尚未完成，不可用近似公式冒充。

**2026-11-02 追加**：第 21 個計算器 `steel_column`（鋼構柱、柱腳基板與基礎螺栓）已上線，
接上 `design_api.py`、`design_cli.py`、MCP 與 `/design` 工作台；詳見
`docs\鋼構柱與基礎螺栓計算SOP.md`。柱腳詳圖繪圖模組仍待補（`tools\wall_section` 只支援擋土牆與排水溝）。

## 5. 各工項的計算邊界

### 5.1 擋土牆

牆型先分成下列家族，不以單一 `gravity` 名稱混用：

| 家族 | 主要幾何 | 穩定來源 | 構材重點 |
|---|---|---|---|
| 重力式 | 梯形或階梯形牆體 | 自重 | 通常免結構配筋，仍需溫度／收縮筋 |
| 半重力式 | 厚牆身、基腳、趾板、踵板 | 混凝土自重＋部分覆土 | 牆身、趾板、踵板、止滑榫 |
| 懸臂式 | 薄牆身＋底板 | 踵板覆土 | 牆身、趾板、踵板、剪力筋 |
| 扶壁式 | 牆身＋底板＋縱向扶壁 | 踵板覆土＋扶壁 | 牆版、扶壁、底板 |
| 加勁式 | 面版＋加勁材＋回填 | 加勁材拉力 | 內部／外部穩定、拉拔與面版 |
| 格籠／砌石 | 分層塊體 | 自重 | 層間滑動、傾倒、材料容許應力 |
| 錨定式 | 牆體＋地錨 | 錨碇力 | 錨碇長度、拉拔、面版與整體穩定 |

第一階段只先完整支援「重力式、半重力式、懸臂式」，因為這三類已有舊 Excel 或現行工具可作基準。
其餘牆型先在型別註冊表保留位置，不可用近似名稱偷套公式。

每個牆型都必須共用：

- 幾何多邊形與形心。
- 混凝土、覆土、水體與其他垂直力。
- 主動土壓、被動土壓、水壓、超載與地震增量。
- 滑動、傾倒、合力位置、承載與整體穩定。
- 常時與地震檢核，逐項輸出 `value / limit / ok / basis`。

### 5.2 箱涵

單孔、雙孔、三孔應由同一參數模型生成：

```json
{
  "cell_count": 3,
  "clear_width_m": 3.0,
  "clear_height_m": 2.5,
  "wall_thickness_m": 0.35,
  "top_slab_thickness_m": 0.40,
  "bottom_slab_thickness_m": 0.45,
  "cover_depth_m": 0.60,
  "length_m": 20.0
}
```

`cell_count` 改變節點與桿件拓樸，不改變外力與構材檢核介面。建議以橫向每單位長度的
2D 剛架作為第一版，輸出頂版、外牆、內隔牆、底板與角隅控制內力。

水理分兩層（2026-10-29 已接線）：`hydraulic_capacity()` 只給曼寧正常水深與滿流上限；
`culvert_hydraulics.py` 依公路排水設計規範 §6.2 算進口控制（附錄 N／HDS-5 迴歸式）、
出口控制（附錄 O 式 O-1／O-2、表 O-1 Ke），取兩者較大值為設計上游水深，再比對
最高容許上游水深（§6.2.1 第1項）與最小斷面（表 6-1）。`inlet_type` 是選填欄位，
沒填就只跑正常水深，避免舊案例基準被動到。

必要載重：

- 頂版覆土與路面超載。
- 車輛活載重經覆土之分佈。
- 側向土壓力、地下水與上浮力。
- 箱涵內水壓力。
- 溫度與收縮。
- 地震時之土層位移或擬靜態土壓增量。
- 常時、地震與施工階段組合。

必要檢核：

- 水力：設計流量、入口／出口控制、最小斷面、覆土厚與容許流速。
- 結構：撓曲、剪力、軸力、裂縫、最小鋼筋與角隅細節。
- 幾何：淨寬、淨高、各部厚度、搭接與保護層。
- 數量：混凝土、模板、鋼筋、開挖、回填、基礎與翼牆。

### 5.3 排水系統

排水應拆成兩層：

1. **流量層**：集水區、逕流係數、降雨重現期、節點流量與匯流。
2. **水理層**：渠道、箱涵、涵管、跌水、連接井與水面線。

第一版先做：

- 網路拓樸與上下游關係。
- 各節點設計流量。
- 渠道／箱涵／涵管容量。
- 流速、出水高與基本跌水消能。

第二版再做：

- 迴水與漸變水面線。
- 進出口控制與尾水。
- 分流、溢流、並聯管渠與都市排水網。

規範體系必須由案件明確指定，不可以在同一案混用參數：

- 山坡地：水土保持技術規範。
- 公路：公路排水設計規範。
- 市區道路：市區道路及附屬工程設計規範。
- 雨水下水道：下水道工程設施標準。

### 5.4 滯洪池

滯洪池不是放大版沉砂池。兩者容量目的不同：

- 沉砂池：截留泥砂體積。
- 滯洪池：削減洪峰，需調洪演算。

核心步驟：

1. 由水文分析產生入流歷線。
2. 建立水位—面積—蓄水體積曲線。
3. 建立水位—孔口／堰／抽水出流曲線。
4. 以 Modified Puls 或水位池法演算。
5. 求最高水位、最大出流量、滯洪量與出水高。
6. 檢核緊急溢洪道、池堤自由高、下游容受與空池容量。

第一版可接受三角形或指定歷線；第二版再支援真實雨型、多峰歷線與上游開發情境。

### 5.5 建築物樑、柱、基礎

第一版以小型建築常用的 2D 平面剛架與等值靜力法為範圍，先建立：

- 樑柱線元素、節點、支承與釋放。
- 靜載、活載、風力、地震與載重組合。
- 樑端彎矩、剪力、柱軸力與彎矩。
- 內力包絡與控制組合。
- RC 樑撓曲／剪力、柱軸彎互制與最小鋼筋。

基礎必須分開支援：

- 獨立基腳。
- 聯合基腳。
- 筏式基礎。
- 樁基礎列為後續，不可用淺基礎公式代替。

必要檢核包含承載、偏心、滑動、傾倒、沖剪、單向剪力、撓曲、沉陷與差異沉陷。
地質參數必須來自鑽探或明確標示為假設值。

## 7. 統一計算結果格式

所有引擎最少回傳下列共同欄位，才容易接報告與查詢台：

```json
{
  "engine": "box_culvert",
  "version": "1.0",
  "code_profile": ["hwdrain107", "rc112"],
  "inputs": {},
  "assumptions": [],
  "checks": [
    {
      "id": "flexure_top_slab",
      "value": 0.0,
      "limit": 0.0,
      "unit": "",
      "ok": true,
      "basis": "rc112:22.2"
    }
  ],
  "governing": {},
  "warnings": [],
  "quantities": {}
}
```

案件檔仍是數量的唯一來源。計算結果不可默默覆寫 `case.json`；應輸出可追溯的
`.calc.json`，再由案件核心明確接收需要的幾何或數量。

## 8. 驗證策略

每一支引擎至少要有四層測試：

| 層級 | 測試內容 | 通過條件 |
|---|---|---|
| 公式單元測試 | 手算例、邊界值、零載重、極端尺寸 | 與封閉解或標準例相符 |
| 舊案基準 | Excel 或已完成案件的逐項數值 | 在明訂容差內，且差異有解釋 |
| 負面測試 | 尺寸衝突、參數越界、規範不適用 | 必須擋下並指出原因 |
| 整合測試 | 案件 JSON → 計算 → 數量 → 圖面 → 預算 → 報告 | 全案回歸與圖數對帳通過 |

不得用「程式有輸出」當作驗證完成。每個控制值都要能和手算、舊案或規範例對帳。

## 10. 介面與 AI 操作方式

使用者可用口語描述案件，例如：

- 「設計一段 40 m、高 3.5 m 的半重力式擋土牆，回填砂土，地下水位 1 m。」
- 「檢核 3×2.5 m 三孔箱涵，覆土 0.6 m，設計流量 6 cms。」
- 「做一個 2 公頃集水區的滯洪池，50 年重現期，容許出流 0.8 cms。」

AI 的操作流程應固定為：

1. 判斷工項與適用規範體系。
2. 檢查必要輸入是否齊全。
3. 缺資料時只問真正會改變結果的參數。
4. 呼叫對應引擎，不以聊天文字自行心算。
5. 顯示控制工況、假設、規範依據與不通過項目。
6. 通過設計閘門後，才產數量、圖面、預算與報告。

規範查詢台可新增「主題 → 條文 → 計算工具 → 案例」的關聯。每張主題卡除既有 `core`
與 `prereq` 外，應逐步加入：

- `calculators`：可執行的引擎與命令。
- `required_inputs`：必要輸入。
- `examples`：已驗證案例。
- `limitations`：尚不可宣稱完成的情境。
