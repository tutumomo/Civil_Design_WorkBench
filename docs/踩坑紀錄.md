## I. A3 圖紙空間／視口／出圖（2026-10-22，智能體「公司的小賤人」實測）

### CADCraft CLI 的坑（最耗時，先看這段）
- **[2026-10-22] `run --cmd` 的格式是 `id {json}`（空格分隔），不是 `id={json}`**。
  寫成 `plot={...}` 會回 `unknown command`。正確：`--cmd 'plot {"path":"...","layout":"..."}'`。
- **[2026-10-22] `plot` 吐出來的是 PDF，不是 PNG**。即使 `path` 寫成 `a3_plot.png`，檔頭仍是 `%PDF-1.4`。
  → 出圖後要用 PyMuPDF（本機 Python 環境已裝 `fitz` 1.26.7）轉 PNG 才能目視檢核：
  `fitz.open(pdf)[0].get_pixmap(dpi=200).save(png)`
- **[2026-10-22] `convert` 只渲染模型空間**（說明寫死 `always model space`）。要看圖紙空間的布局，**只能用 `plot` 帶 `layout` 參數**。
- **[2026-10-22] `convert` 可以直接吃 `.dwt`**（AC1032/DWG2018 也行），輸出 `.dxf`，這是把公司圖框樣板轉進程式的捷徑：
  `cadcraft-cli.exe convert A3圖框.dwt A3_frame.dxf`

### ezdxf 的坑
- **[2026-10-22] `draw_layout()` 不會渲染視口內的模型空間內容**。渲染圖紙空間布局時，中央視口一片空白（實測非白像素僅 0.55%）。
  → 這是**工具限制不是圖有問題**。要出圖檢核一律走 CADCraft `plot`，不要用 ezdxf 畫布局。
- **[2026-10-22] `doc.styles.add()` 的 `font` 是 keyword-only 參數**：`doc.styles.add("TOMO", font="gbenor.shx")`；
  塞進 `dxfattribs={"font": ...}` 會報 `TypeError: missing 1 required keyword-only argument: 'font'`。
- **[2026-10-22] 用 `Importer` 併兩個 DXF 時，目標文件要先有同名文字樣式**，否則匯入的 TEXT 會掉樣式。
  → 併檔前先 `if "TOMO" not in doc.styles: doc.styles.add(...)`。

- 標題欄欄位標籤（TEXT）與值的位置：設計/繪圖/日期在 `x 93.8~153.5`、工程名稱/圖名在 `x 174.3~245.4`、
  比例尺在 `x 245.4~262.4`、圖序/圖號在 `x 394.0~410.27`；值用 `BOTTOM_LEFT` 對齊填在標籤右側。

### 視口比例換算（模型單位＝公尺時）
```
view_height(模型m) = 視口高度(mm) × 比例分母 / 1000
例：258.45 mm × 600 / 1000 = 155.07 m
模型覆蓋寬 = 視口寬(mm) × 比例分母 / 1000
例：400.24 mm × 600 / 1000 = 240.14 m
```
- 給 `site_basemap.py` 的 `--width / --height` 就用上面算出來的模型覆蓋尺寸，兩邊才會剛好對齊。
- 驗算：`view_height × 1000 / 視口高度 = 實際比例`，要剛好等於分母。

### 流程建議（以後照這個順序做，不會重工）
1. `site_basemap.py` 產模型空間線稿（`--width/--height/--scale` 依目標視口算）
2. 併檔前**刪掉線稿自帶的 `90_圖框/91_指北針/92_比例尺/93_說明`**（約 20+ 個實體），這些要改放圖紙空間
3. `Importer` 併入 A3 圖框 DXF → 刪樣板舊 VIEWPORT → 重建視口
4. 指北針、比例尺放**圖紙空間**（固定 mm 尺寸，不隨比例縮放）；比例尺每格長度 = 圖面 mm × 比例分母 / 1000
5. `plot` 出 PDF → PyMuPDF 轉 PNG → 看非白像素比例判斷有沒有渲染出來
6. 重讀 DXF 驗 `$INSUNITS=6`、`$MEASUREMENT=1`、TOMO 字型、audit 錯誤數

- **圖框→DXF 的 viewport**：只寫 `view_center_point` 沒用，AutoCAD 開啟後 view center 仍是 (0,0)。
  必須同時寫 `view_target_point`（群碼 17/27/37）與 `status=1`，view_height 才會落在測點上。
- **公尺圖面的比例換算**：模型單位＝公尺時，1:600 的 viewport 比例係數是 **0.6**（1 mm 紙 = 0.6 m），
  不是 600。`viewport_set_scale(600)` 會變成放大 600 倍（view_height 0.43 m）；正確值是 `0.6`

## K. Antigravity 實戰經驗補充（2026-10-22，A3 1:600 現況平面圖比拼任務）
- **Windows Python 套件載入順序閃退坑（OpenMP / GUI DLL 衝突）**：
  - 在 Windows 下若先 `import cv2` 再 `import matplotlib` 或 `shapely`/`pyproj`，會因 OpenMP (`libiomp5md.dll`) 衝突直接無報錯閃退 (`Exit code 1`)。
  - **解法**：強制第一行寫 `import matplotlib; matplotlib.use('Agg')`，接著依序 `import shapely`、`import pyproj`，最後才 `import cv2` 與 `import ezdxf`。
- **`EMAPX99` (Zoom 20) 水密路緣萃取法（解決白底道路與背景連通問題）**：
  - `EMAPX99` 在 Zoom 20 可正常取磚（`~0.136 m/px`），雖然道路與街廓背景同為白色 `#FFFFFF`，但中間隔著 1px 灰色路緣線 (`RGB 195..214`)。
  - **解法**：將所有非純白像素 (`RGB < 250`) 做 `2x2` 膨脹 (`cv2.dilate`) 形成 100% 4-連通水密阻隔牆，再拿 OSM 道路中心線沿線取樣點作為種子點 (`connectedComponentsWithStats`) 挑出屬於道路的白色連通區塊並膨脹 1px 還原至路緣中心，即可獲得完整無斷線、含路口圓角的街廓道路邊線。
- **道路彎道平滑化與房屋主軸正交化**：
  - **房屋**：以各邊長度加權計算 `4*θ` 圓周平均角求得每棟房屋真實方位角 (Azimuth)，旋轉對齊主軸後將 `±15°` 內近正交邊拉直，再轉回原方位角並以 `buffer(0)` 修復拓樸；先對建物遮罩做 `MORPH_CLOSE` 可消除超商/停車場圖示造成的小破洞，同時保留 `>= 6 m²` 的真實中庭天井。
  - **道路與河道**：先 `simplify(0.5~0.6m)` 消除像素階梯，再對轉折角 `4°~70°` 的彎道節點做 2 階 **Chaikin Corner-Cutting**，直線段維持筆直、彎道自然圓順。
- **`CADCraft CLI` 完整支援圖紙空間 `VIEWPORT` 渲染與出圖**：
  - 在 `ezdxf` 建立 `VIEWPORT` 時設定 `status=2`、`view_center_point=(cx, cy, 0)`、`view_height=vp_h * 0.6`（維持 `view_target_point=(0,0,0)`），並將 `id=1` 的 Paper Space 總視口對準 `(210, 148.5)`，即可直接用 `cadcraft-cli.exe run file.dxf --cmd 'plot {"path":"out.pdf","layout":"全區工程位置圖","landscape":true,"plotArea":"layout","fit":false,"scale":1.0}'` 與 `preview` 指令完美渲染包含視埠內模型內容的 A3 PDF 與高解析 PNG！
  - 在 Windows 呼叫 `cadcraft-cli run --cmd` 時，務必透過 Python `subprocess.run` 傳遞參數陣列，避免 PowerShell 剝除 JSON 內雙引號。

## P. 鄉道／農路現況道路邊線萃取（2026-10-26，MiniMax Code，AC刨鋪工程；並採 Gemini 2026-10-26 同村案例）

- **EMAPX99 通用電子地圖「看起來全白」不代表沒有路**：本案鄉道沿線抽查
  `emap_EMAPX99_TWD97.png` 在 0.5 m 取樣間隔下全是白像素，一度誤判「此鄉道無圖面」，
  **實際上灰緣線存在但只有 1 px 寬，取樣間隔稍粗就整個跳過**。
  → **判讀圖面是否存在，必須用 0.1 m（1 px）間隔取樣，或直接做灰緣連通分析**，
    不要用目視印象或粗間隔抽樣下結論（本案的錯誤結論就長在這裡）。
- **兩種可用做法**：
  1. **2D 區塊生長法**（Gemini 2026-10-26 實作，適用 EMAP 有完整道路面繪製者）：
     灰緣 → 7×7 閉運算封口 → 灰緣/建物/水體聯集當牆 → 白區 4-連通分區 →
     以 OSM 中心線為種子選區 → 膨脹回灰緣中線 → 等值線 → 保角 Chaikin。
     **優點：整條路一次成型，線條天生平順。**
  2. **灰緣直線萃取法**（本次新增，適用鄉道：電子地圖只有細灰緣、沒有道路面填色）：
     直接取灰緣像素（`|R-G|≤6 且 |G-B|≤6 且 160≤R≤242`）→ 篩出中心線走廊
     (±14 m) 與里程區間 → 全段偏移直方圖找**兩個主峰**（左右路緣）→
     逐里程取各群中位偏移 → 大窗移動平均 → 平順重建。
     成果路寬中位 5.55 m、變化 3.67~6.18 m，線條平直且貼合路面。
- **絕對不要用「逐斷面 1D 橫向掃描正射影像」來畫鄉道邊線**（本次 v1 的做法）：
  裸土彩度與鋪面同樣低（0~6），林蔭段鋪面亮度掉到 55~100，掃描結果必然階梯化、
  跳動、彎道處左右線交叉；靠中位數濾波與移動平均只能掩蓋、不能根治。
  **正確順序是「先取得向量化的道路邊線（電子地圖灰緣），再疊加正射影像檢核」。**
- **灰緣萃取的三個致命坑**（全部踩過）：
  1. 兩側偏移必須用**同一組車站陣列**計算，否則第二次外推時車站已延長而偏移未同步 →
     邊線錯位、走廊多邊形變成碎片（面積只剩 481 m²）。
  2. 車站延伸後必須**依里程排序**；把低端延伸接在高端之後會造成折返，邊線長度膨脹 3 倍。
  3. OSM 中心線可能整條偏在路的一側（本案偏 5.5 m），樁號、斷面、面積都要以
     **左右路緣中線**為基準，否則斷面切歪、面積少算一半。

### U.2 真正的原因

- 規範入庫若「一頁一頁渲染來看」，一個 session 很容易累積上百張；**撞線後不是那一張的問題**，

- 唯一解法：**開新對話**（新 session 不帶舊圖片）。在原對話繼續任何工作都會 400。

### U.3 硬規定（本專案所有智能體）

1. **核條文／核表格預設不看圖**，改用文字層座標抽表：

   - 表格有合併儲存格時，數值會落在兩條篩線之間：**以最近的篩孔列為歸屬**

## V. 規範取頁 `--part` 在含空白的檔名上會靜默失敗（2026-11-01，Codex/Cindy）

### V.1 症狀

- `page_table.py hwbridge --page 85 --part "第五章 基礎"` → `find_pdf` 回 `None`，
  再 `fitz.open("None")` 直接炸；更早的 `regs_vtool.py page` 則是 `continue` 掉、**什麼都不印**（更危險）。

### V.2 原因

- `page_assets.find_pdf` 原本用 `next(d.rglob(part), None)`。實測 `Path.rglob("第五章 基礎")` 回空清單，
  但 `Path.glob("第五章 基礎.pdf")` 與 `Path.glob("**/第五章 基礎.pdf")` **都找得到** →
  路徑含空白時 `rglob` 的無萬用字元樣式會失效（不是權限、也不是編碼問題）。
- 而且原本的 `rglob(part)` 比對的是「不含副檔名的完整檔名」，實際上永遠對不到 `*.pdf`，
  等於 `--part` 從來沒成功過；找不到時又回 `None`，呼叫端默默跳過 → 看起來像「這條沒有 PDF」。

### V.3 修法（已改）

- `find_pdf` 改成：先列出該規範資料夾內所有 `*.pdf` 的 `stem`，再以「完全相同 → 忽略大小寫 → 包含字串」
  三段比對；**給 `part` 卻找不到就回 `None`，不再退回整本 PDF**（避免頁碼對錯還不出聲）。
- `page_table.py` 在 `pdf is None` 時直接 `sys.exit` 並印出 `available`（可用 part 清單）。

### V.4 現在怎麼取頁

- 分章 PDF（公路橋梁、鋼構 99）：`--part "第五章 基礎"`、`--part "(一)ASD 容許應力設計法"`（**包含字串即可，不必全名**）。

  （已入庫的 hwbridge 條目 p.372-373 屬這一本）。

## Z. 猜頁碼會一直抓錯頁：印刷頁碼 → PDF 頁 對照表（2026-11-02，Codex/Cindy）

### Z.1 症狀

- 子代理回報「這頁沒有目標表／式」，換頁重試仍找不到；或抓到頁了但內容是別的章。
- 同一條文反覆重抓 2~3 次才對，浪費大量圖片預算（每 session 上限 200 張，見 §U）。

### Z.2 原因

**PDF 檔序 ≠ 頁面上印的頁碼**，而 DB 的 `unit.page` 記的是**條文起頁**（表常在下一頁）。

實例：

| 規範 | PDF 第 N 頁 | 頁面上印的 |
|---|---:|---|
| 公路路線設計規範 115 | 44 | 3-17 |
| 公路排水設計規範 | 132 | -110- |
| 市區道路及附屬工程設計規範 | 36 | 道路工程設計篇 3-4 |
| 建築物耐風設計規範 | 84 | 76 |

2026-11-02 第二輪消化的 27 條待核中，**14 條就是「目標在下一頁」**。

### Z.3 修法（已做成工具）

`tools/regs/page_index.py`：逐頁用**座標**（頁首／頁尾 12% 帶內）辨識印刷頁碼，建索引。

```bat
python -E -P -X utf8 tools/regs/page_index.py build <src>
python -E -P -X utf8 tools/regs/page_index.py find  <src> <印刷頁碼>
```

索引快取在 `_temp\regs_pages\_page_index\<src>.json`（可重建、可整批刪除）。

**兩個必要條件**（改動時勿退化）：

1. **必須用座標，不能用文字層前後字串**——頁面開頭可能是「3-17表3.8.1.2複曲線…」，內文的「3-8」會被誤判為頁碼。
2. **頁碼常被拆成多個 word**（「3-17」＝`'3'`、`'-'`、`'17'`），必須把**同一橫列**的 token 依 x 座標串接後再比對格式。

### Z.4 整頁低解析圖會讓子代理讀錯公式

110 dpi 整頁圖上，公式的「上標位置」「括號外的 1−」「不等號是 ≤ 還是 ≧」常被讀錯。
本輪實際被讀錯並改正的例子：

| 條目 | 整頁圖讀成 | 260~420 dpi 局部裁圖確認 |
|---|---|---|
| 公路路線 3.5.3 式(1) | 平方罩整個中括號 | **方括號外還有一個「1−」**，平方只罩 (1−R_min/R) |
| 市區道路 3.4.3 式(4) | 分母 R−R_min | **分母 R_r−R_min** |
| 公路施工 02321 4.1.3 | 不等號「≤」 | **「≧」**（讀反了，改正後邏輯自洽） |
| 公路路線 3.9 加寬 U_c | `2.5+√(R²−X²)−R+Y` | **`2.5+√(R²+X)−√(R²−Y)`**（讀法不同會使 ΔW 得 109 m） |

**修法**：用 `tools/regs/page_crop.py` 裁局部並提高解析度（260~420 dpi），座標以 PDF point 為單位，
從 `page_table.py` 或 `pg.get_text('words')` 的 x0/y0 取得。頁碼／頁眉通常在 y≈780（頁高 842），公式本體在 y 500~640。

### Z.5 整表跨頁／合併格：文字層會錯亂

文字層（`_page_texts`）是**逐欄順序輸出**，多欄表格的「縣市」欄合併格會被打散，
逐行讀會得到錯亂的歸屬。**用 PyMuPDF 的表格結構 API**：

```python
tabs = page.find_tables()        # 正確處理合併格（續行列為 None）
ex = tabs.tables[0].extract()    # 二維陣列，含表頭
```

實證：`seis113` 第 2.18 條之 SDS 鄉鎮市區表，用文字層只得 314 列且縣市錯亂；
改用 `find_tables()` 得 **327 列 ＝ 全台 368 鄉鎮市區 − 臺北市 12 − 新北市 29**，22 縣市齊備、無重複 ✓。

**沒有 PDF 的純文字規範**（`btr_*`、`swc_*`、`sewer_std`、`traffic_sign` 等 15 份），
表格以方框線（`┌─┼─┤`）表示，可**程式解析**：逐行以 `│` 切欄、遇內部框線結算一列。
實證：`btr_equip` 第 37 條衛生設備表（9 類 × 30 列）即以此法補齊器具個數。

### Z.6 B 類 Phase 2 的六個坑（2026-11-02，Codex/Cindy）

1. **`qualitative` 這一桶不可信**：Phase 1 抽驗 51 條錯 2 條（4%）；Phase 2 對「公式訊號最高的 28 條 qualitative」逐條讀原文，**約 4 成其實有算式**（hwbridge104 7.3.4／7.3.5 整套柱設計式、hwbridge 8.17.2／8.17.3／8.18.1 預力撓曲強度、rc112 17.6.2.1.1、17.7.2.1.3、9.6.4.2、seis113 10.3.2、steel99 6.4／9.4.2／9.4.6、hwbridge 8.21.7）。**主因是把「工作台未實作」的範圍理由寫成 qualitative**——範圍決定應標 `out_of_scope`，qualitative 只能用於「確無算式或數值表」。篩選法：`tools\regs\audit_qualitative.py`（式號 `(8-13)`、`式7.5-2`、`=`/`≤`/`≥` 與小數個數打分，由高分往下讀）。
2. **`payload_check --library` 不檢查「測試輸入是否違反條目自己的 conditions」**，只有 `verified_selftest` 會抓到（`VerifiedError: 不符適用條件`）。新增條目後**一定要跑 selftest**，不能只看 payload_check 的 0 problem。例：預力撓曲強度翼板斷面測試用 As=15，算出 Asf=31.5>As，payload_check 過、selftest 才炸。
3. **條目 `clause` 必須是 unit 資料庫裡實際存在的條號**（selftest 的 `clause exists` 檢查）。9.6.4.2 這類子條不一定獨立成 unit，會併在 9.6.4.1 的 unit 裡——此時用 **unit 的條號**，把子條號寫在標題與 notes。
4. **文字層小數點常被倒置或拆開**：`20 . 1`＝1.20、`5 .0`＝0.5、`0.1`＝1.0、`17.2`＝117.2（首位 1 被分離）、`8425`＝842.5。**判讀方法**：①雙單位（kgf／MPa）比值應為 10.2（係數）或 3.19（開根號）；②兩段式在轉折點必須連續（本輪用來還原 11.2-11 的 √(1.4−fa/Fy)、11.2-13 的 √(1.9−1.2fa/Fy)、9-74 的正弦過渡式）；③與 AASHTO／ACI 單位換算對照。**根號、分數線、上下標在文字層常整個消失**，不可只憑符號順序。
5. **初稿最常見的兩種錯**（都是靠「寫測試→看結果量級」抓到，不是靠重讀）：(a) **漏掉分母裡的符號**（9.2.7 把 `1.70·A·Fe` 讀成 `1.70·Fe`，T 是力、Fe 是應力，量綱不通，測試報『已達挫屈』才發現）；(b) **單位制搞錯**（9.3.7 的 1089、5098.6 是 kgf/cm² 制，用 tf/cm² 輸入會差 1000 倍；Fy=2500 時 b/t 上限應 21.8，我的測試得 688.7）。**每個條目至少要有一個「手算得出預期量級」的測試。**
6. **shell heredoc 又吃掉反斜線**（`\f`＝換頁、`\r`＝CR）：用 `cat > x.py <<'EOF'` 寫含 LaTeX 的 Python 時，`\frac` 變成「換頁＋rac」、`\right` 變成「CR＋ight」，產生 `unterminated string literal`。**含 LaTeX 的檔一律用 write／edit 工具寫**；已被吃掉的要用 edit 的 JSON 逸出（`\f`＝換頁）精確比對後改回。
7. **skip 理由寫「已於前批登錄」必須驗證**：hwbridge 5.5.3（單樁承載力，式5-4~5-7＋表5.4~5.6）的 qualitative 理由寫「同 5.5.3 已於前批登錄」，實際庫內完全沒有——**核心設計式整段漏掉**。skip 理由若引用其他條目，必須附上條目 id，並由腳本檢查該 id 存在。
8. **續審 qualitative 的實測命中率（2026-11-02 第二輪）**：依式號與運算符打分、由高分往下讀，前 130 名中約 3 成有算式或表；分數低於 5 的 150 餘條（hwdrain 4.x~9.x 純條文、hwconst112 16526 章、符號表）抽看皆確為無算式。**高命中區是：預力／橡膠支承／樁基礎／耐久性表／雙向版細部／錨栓 ca1 類小公式；低命中區是：總則、定義、施工規定、計價條文。**

### Z.7 視覺管道實測（2026-11-02，10 個目標，全數由子代理讀 260 dpi 原頁圖）

## AA. 箱涵車載、逐面配筋與每延米數量（2026-11-03，Codex）

### AA.1 「漏計車載重」其實是固定 10 kPa 藏在程式裡

- **症狀**：使用者說箱涵計算「好像漏計車載重」。查程式發現

### AA.2 Excel 文字標籤會騙人：以儲存格數值為準

- **症狀**：`箱涵(雙孔、三孔).xls` 的 H-20 S-16 低覆土列寫

- **修法**：用 `xlrd` 逐格 dump `B74～B94`，同時印文字列與數值列；

- **教訓**：引用 Excel 公式時，**至少做一次「數值反推」**；只抄文字標籤

### AA.3 40T 工作簿是「整片均佈」，不是局部輪壓

- **症狀**：`箱涵(單孔、雙孔).xls` 的 40T 列把 `Pwh=7.2222 t/m²` 直接

  局部輪壓，設計彎矩會比工作簿小。
- **做法**：程式保留局部輪壓（總輪載與實際相符），另提供 `custom` 讓人
  輸入整片均佈值完全復刻工作簿；文件與警告都要寫清楚這個差異。
- **教訓**：**「與工作簿一致」不能隨便講**；先確認工作簿是把載重放在
  整片還是局部，否則會誤導使用者。

### AA.4 逐面配筋不能「兩個方向取小」

- **症狀**：早期版本把上下（或左右）配筋不同時的兩個彎曲方向取較小

- **教訓**：**配筋是「面」的屬性，不是「構材」的屬性**；頂版外側／內側、

- **原因**：兩支檔都在 `tools\boq\`、`tools\report\`，`parents[2]` 是
  `<root>\tools`，不是專案根；`case_package` 先把自己的路徑插進 `sys.path`
  才讓它「看起來正常」。
- **修法**：改 `parents[1]`（=`<root>`）。判準：`python tools\boq\boq_build.py -h`
  與 `python tools\report\make_report.py -h` 都要能獨立執行。
- **教訓**：**工具必須能脫離呼叫者獨立啟動**；只測「上層呼叫得到」會漏掉
  路徑寫錯，等到單獨重跑或換工作目錄才爆。

### AA.10 回歸讀舊的 `cases\<案名>\out` 與舊交付狀態 → 假通過

- **症狀**：改壞工具後 `regression.py` 仍顯示全數 ✓，但 `out\<案名>\` 是舊產物。
- **原因**：回歸沿用 `cases\<案名>\out`（舊位置），又用該資料夾的
  `交付狀態.json` 判定 ok；檔案沒更新，狀態自然是舊的 `ok=true`。
- **修法**：一律輸出到 `out\<案名>\`、顯式傳 `--out-dir`，`ok` 只看本次
  退出碼與本次各軸 `[OK]/[FAIL]`；舊狀態檔不得覆蓋。
- **教訓**：**驗證要看「這次跑的」，不是「上次留下的」**；任何「讀既有狀態」
  的檢查都要能證明檔案時間戳/內容屬於本次執行。

### AA.11 道路案只剩刨鋪範圍 DXF、沒有 `road_edges_meta.json` 時不可跳過對帳

- **症狀**：AC 案回歸 `刨鋪面積 851.09 → 無值`，但圖與數量其實都在。
- **原因**：`run_drawing()` 只認實測邊線檔；檔被清掉就印「未量測」並放行，
  等於讓未對帳的 AC 體積過關。
- **修法**：三段式——有 meta 就重生；沒有 meta 但既有 `*_刨鋪範圍_TWD97.dxf`
  存在就沿用並重跑 `dxf_takeoff.py`；兩者都沒有才 `exit 1`。
- **教訓**：**對帳缺少來源時要失敗，不是加註記就放行**；「沿用既有圖」必須
  重新量測，不能直接抄舊 JSON 的 `area_m2`。

### AA.12 回歸永遠紅燈，會把新失敗蓋掉

- **症狀**：`擋土牆3m重力式_北屯民政里` 因案件 `boq.items` 為空長期 NG，
  `regression.py` 每次都 exit 1；新改壞的案子混在裡面看不出來。
- **修法**：基準已記錄 `ok=false` 的案件列為「既有未通過」，仍會印出但
  不計入本次失敗；**新變紅**（基準 ok=true 或基準沒有）才 exit 1。
- **教訓**：**已知缺口要顯性列出、但不能讓它癱瘓訊號**；不可用 `--update`
  把新失敗一併寫成基準。

### AA.13 新建箱涵案件的樣板還停留在舊的假設值

- **症狀**：既有 `cases\箱涵三孔測試\case.json` 已改用 `rebar_kg_design` 與
  H-20，但 `case_new.py` 產出的新案仍是 `rebar_kg`（90 kg/m³ 假設）與
  `traffic_load_kpa=10`（被視為 custom 定值，不是輪載換算）。
- **修法**：樣板的 BOQ 改 `qty_from: "rebar_kg_design"`、模板名稱補「頂版底面」，
  `culvert` 明確給 `traffic_type: "h20"`、`traffic_lanes: 4`、`traffic_load_kpa: 0`。
- **教訓**：**修正既有案件不等於修正產線**；`case_new` 的樣板要跟引擎預設
  一起改，否則下一個新案立刻退回舊錯。

## AB. 擋土牆配筋：深度定義、基腳鋼筋與圖數對帳（2026-11-04，Codex）

### AB.1 扶壁 T 梁的 d 是水平深度，不是垂直斜面的距離

- **症狀**：`counterfort_wall._counterfort_design()` 用
  `(ts + heel) × sinθ` 算有效深度；H=8 m 案得到 d=4,023 mm。
- **原因**：扶壁是豎向懸臂 T 梁，彎矩繞**水平軸**作用；基底斷面的
  d 是「水平」由牆板前面量到扶壁背面（`ts + heel`）。乘 `sinθ` 等於
  把斷面切在斜背的法線方向，與實際受力方向不符。
- **修法**：`d = (ts + heel) × 1000 − cover − 30`；H=8 m 案 d=4,515 mm。
  修正後 As,min 由 5,364 增為 6,020 mm²，主筋 7-D32 → 8-D32。
- **附帶修正**：ACI 318 §11.4.6.1，`Vu > 0.5φVc` 即須最少剪力筋；
  新增 D13@600 兩肢（H=8 m 案），不再因混凝土剪力足夠就完全省略箍筋。
- **教訓**：**「偏保守」不等於「定義正確」**；錯的 d 會同時影響 As,min、
  剪力筋與鋼筋量，不能只看檢核有沒有過。

### AB.2 兩扶壁間標準斷面 vs 含扶壁分攤的混凝土量

- **症狀**：扶壁案 S-01 圖面面積 6.36 m²，數量模型 8.824 m²，對帳差 27.9%。
- **原因**：S-01／S-02 畫的是兩扶壁間標準斷面（扶壁以虛線表示），
  但混凝土體積必須含扶壁分攤 `0.5×(heel+ctop)×H×tc/S = 2.464 m²/m`。
  兩者都對，錯的是拿總量去比實體斷面。
- **修法**：`qty_models` 新增「實體斷面面積」派生鍵（僅扶壁式扣除扶壁
  分攤，其餘牆型等於 `section_area_m2`）；`dxf_takeoff` 優先用它對帳。
- **教訓**：**圖與數量必須先講清楚「切在哪裡」**；典型斷面、含肋斷面、
  每延米平均量是三種不同東西，不能共用一個鍵。

### AB.3 錨定式基腳不能只畫不計

- **症狀**：錨定式 S-02 已畫基腳上下層鋼筋，但 `design_anchored_wall_steel()`
  只算牆面四向筋與承壓區補強網，基腳鋼筋量為 0。
- **修法**：依 `0.0018bh` 配上下層橫向筋（D16@220）＋縱向分布筋，
  H=7 m 案由 288.25 增為 326.43 kg/m；`spacing_candidates()` 與 S-02
  配筋表同步讀 `base_rebar`。
- **教訓**：**圖上畫了鋼筋，數量表就必須有那一列**；反過來說，配筋表
  沒有長度與支數時，數量模型不能自己猜。

### AB.4 自動比例不能只估混凝土多邊形

- **症狀**：3 m 重力式估 3.35 m 寬 → 選 1:20，實際 bbox 3.79 m，
  出圖前被 183 mm 視口上限擋下（exit 1）。
- **原因**： estimation 只取 `wall_geometry` 的混凝土點，沒有計入右側
  背填／反濾層、尺寸線與鋼筋標註。
- **修法**：右側餘裕由 0.50 改 0.95 m；加勁式另把加勁材長 L、錨定式把
  前 2 m 地錨納入外廓。
- **教訓**：**auto scale 要估「整張圖的 bbox」，不是只估結構體**；
  寧可先選大一級，也不要出圖前才失敗。

### AB.5 加勁式沒有底板，圖例卻印「底板筋」

- **症狀**：MSE 的 S-01 鋼筋圖例沿用一般牆型，出現
  「C D16@200 底板筋（上下層）」，但加勁式只有 RC 面版，沒有底板。
- **原因**：`build_paper()` 的非配筋表分支只分「邊坡／排水溝／重力式／
  其他」，MSE 落進「其他」；保護層也跟著用牆體的 75 mm，與同圖說明
  「面版保護層 50 mm」互相矛盾。
- **修法**：新增 MSE 專屬圖例（面版水平筋、面版豎向筋、保護層 50 mm）；
  `_cover_default` 由牆型決定（MSE／排水溝 50、其餘牆 75）。
- **附帶修正**：MSE 的「4 基礎埋入段」原本標在加勁區中段，改到地面線
  以下的面版埋入段；「6 基礎開挖線」移到開挖線左端外側。
- **教訓**：**圖例是圖的一部分，不是免責聲明**；共用圖例前先問「這個
  牆型有沒有這個構材」。

### AB.6 報告圖說寫「1:auto（自動）」

- **症狀**：設計報告第 12 章嵌圖的圖說顯示「A3，1:auto（自動）」。
- **原因**：`case.json` 的 `section.scale` 是 `"auto"`；實際比例要等
  `make_wall_section.py` 算完模型外廓才決定，`case_core` 直接把字串
  印進圖說。
- **修法**：`_attach_section_figure()` 新增 `_dxf_scale()`，從 DXF 各
  版面（圖框標題欄、說明）以 `1:N` 正規式讀回眾數；讀不到才退回 1:20。
- **教訓**：**推導值不要用輸入值假裝**；能從成品讀回來的，就不要在
  報告端再猜一次。

### AB.7 回歸對進階牆型只記 design_error

- **症狀**：`baseline.json` 的扶壁／錨定／加勁三案只有 `design_error`
  「不支援的擋土牆牆型」，沒有 FS、鋼筋量、承載應力。
- **原因**：`regression.py` 直接呼叫 `retaining_wall.analyse()`，該引擎
  只認 gravity／semigravity／cantilever；進階三型一拋錯就被外層
  `except` 記成 `design_error`，回歸因此「看起來有跑」卻什麼都沒追蹤。
- **修法**：改走 `wall_system.analyse()`／`rebar_design()`；以檢核項的
  `unit=="FS"` 辨識安全係數，`kPa` 另記 `承載應力_kPa`，避免把容許
  承載力誤當 FS。基準已 `--update` 納入六型。
- **教訓**：**回歸的覆蓋率也是要被測試的**；只追蹤三型，另外三型改壞
  了也會顯示全綠。

## AC. 多智能體協作：共用工作區的交接與落地（2026-11-04，Codex）

本專案同時有 Codex、Claude、Gemini／Antigravity、WorkBuddy 等智能體在**同一個
工作目錄**作業，且常常是「前一個 agent 做完、下一個 agent 接手收尾」。以下五條
都是本輪真實踩到或差一點踩到的坑。

### AC.1 交接摘要不是事實來源，白名單要用基準反查

- **症狀**：接手時的交接摘要列了本次 commit 白名單，但漏掉
  `cases\擋土牆4m半重力式\`（untracked）。該案其實已寫進
  `tools\selftest\baseline.json`，且 `ok=true`。
- **後果**：若照摘要 stage，本地回歸全綠、push 後別台機器 clean clone
  會少一個案件，`regression.py` 直接失敗（或更糟：被當成新失敗）。
- **做法**：以 `baseline.json` 的案件鍵**反查** `cases\` 目錄，逐案確認
  `git status` 是已追蹤、已修改還是 untracked；untracked 的案件資料夾
  要整包納入（`case.json` ＋ 交付物），不能只 stage `case.json`。
- **教訓**：**摘要只用來起點，不用來結案**；權威順序是「基準檔 → 實際
  檔案 → 測試輸出 → 摘要」。

### AC.2 共用工作區禁用 `git add -A`

- **症狀**：本輪開工時 `git status` 有 60 幾筆修改／刪除／untracked，
  包含其他 agent 的字型文件、MCP 接線、Blender、IngeTrazo、`tools.excel`
  原始檔與 `.bak`。
- **做法**：先寫下「納入 commit」與「保留不動」兩張清單（收工 SOP §1），
  只對白名單路徑 `git add -- <path>`；commit 前用
  `git diff --cached --name-only` 逐筆核對。
- **教訓**：`git add -A` 在單人 repo 是方便，在多 agent 共用工作區是
  **把別人的半成品一起送上線**。

### AC.3 同一個檔案被兩個 agent 改：要 hunk 級 stage

- **症狀**：`AGENTS.md` 同時有別人的字型段落、`INGETRAZO_HOME`、
  §5.1 MCP 接線，以及本輪的擋土牆配筋分流與觸發器。整檔 stage 會把
  無關工作混進本次 commit。
- **做法**：用 `git diff -- AGENTS.md` 先看全部 hunk，另存一份只含本次
  hunk 的 patch（保留 `diff --git`／`---`／`+++` 檔頭），再
  `git apply --cached <patch>`；完成後 `git diff --cached -- AGENTS.md`
  確認只剩本次段落，工作區其餘修改仍在。
- **教訓**：**檔案不是最小單位，hunk 才是**；共用檔案要先 `git diff`
  再改，避免用「我最後寫入」覆蓋別人的未提交工作。

### AC.4 子代理回報「完成」≠ 已驗證

- **症狀**：子代理回報三案全軸通過、E1~E18 零錯誤，但沒有留下可重跑的
  指令與輸出；回報中的數字與 `baseline.json` 對不起來時無法判斷誰對。
- **做法**：接到完成回報後一定自己做四件事：①重跑指定測試並看退出碼；
  ②讀 `out\<案名>\` 的檔案時間戳確認是本次產出；③抽看 PDF→PNG 的
  圖面（比例、圖例、尺寸）；④把回報數字與基準／報告／預算三處對帳。
- **教訓**：**完成回報是待審文件，不是驗收證明**；驗收要看可重現的
  指令與成品，不看文字。

### AC.5 平行修改要先認頒 ownership

- **症狀**：多個 agent 同時改 `tools\design\` 與 `tools\case_package\`，
  曾出現同一支工具被兩份 patch 前後覆蓋，後者以舊版為底，悄悄把前者
  的修正吃掉。
- **做法**：開工先講清楚「誰負責哪些檔案」；動筆前 `git diff -- <file>`
  確認沒有他人未提交變更；若必須共用，先把自己的修改縮到最小 hunk，
  完成後立刻跑該模組的 selftest，並在回報註明「我改了哪些檔、哪些沒動」。
- **教訓**：**共享目錄不會自動合併語意**；檔案層級的鎖沒有意義，只有
  「先看 diff、再改、改完重跑」能保證結果。

### AC.6 工作區全綠 ≠ commit 可重現：一定要跑乾淨 checkout

- **症狀**：收工前在原工作區跑 `regression.py`，11 案全綠；push 後用
  `git worktree add --detach _temp\cleancheck HEAD` 重跑，只剩 2 案過。
- **根因（兩層）**：
  1. `boq_build.py` 與 `make_report.py` 的 `parents[1]` 路徑修正、以及
     `verify_report.py` 的 `--allow-no-figures`，都只存在工作區，沒進版。
     乾淨 checkout 一跑就 `ModuleNotFoundError: project_paths`，所有案件
     的預算與報告軸整批失敗。
  2. 補完上述檔案後仍有 3 m 重力式失敗：`case.json` 還寫死 `scale: 20`，
     新版視口 189.4 mm 超寬；`scale: "auto"` 的修正也沒進版。
- **做法**：把「乾淨 checkout 重跑全案回歸」列為收工必要步驟（見
  `docs\專案收工SOP.md` §4.1）。失敗時先看 `out\<案名>\_log_*.txt` 的
  第一行 `CMD:` 與 traceback，回溯是哪個檔案的哪個版本沒進 commit。
- **教訓**：**回歸測試驗的是「你電腦上的檔案」，不是「你推上去的
  commit」**；只有乾淨 checkout 能證明後者。多智能體環境尤其如此，
  因為別人的修正很容易只停在共用工作區。

## AD. 計算器有引擎 ≠ 工作台有功能（2026-11-04，Codex）

- **症狀**：使用者同時看本機與線上「工程設計工作台」，擋土牆計算器
  都找不到配筋設定，也看不到配筋結果；但 `rc_design.py` 與
  `case_package` 產線其實早就在算配筋。
- **根因（兩層）**：
  1. `design_api._run_wall()` 直接 `return RW.analyse(...)`，從未呼叫
     `rc_design.design_wall_rebar()`；`_wall_field_rules()` 只有穩定分析
     的 5 個欄位，`retaining_wall.format_report()` 也只印穩定檢核。
     功能存在於引擎與 CLI／案件產線，但**沒有接進工作台契約**。
  2. 修好本機後，Cloudflare 仍是舊版：線上 catalog 標題還是
     「擋土牆穩定分析」。`/api/design/health` 回 `ok=true` 只代表服務活著，
     **不代表版本是新的**。
- **修法**：
  1. `_run_wall()` 兩條 return 都走 `_attach_wall_rebar()`；新增
     `_WALL_REBAR_KEYS`、`_wall_concrete()`、`_rebar_check()` 與
     `_wall_rebar_checks()`，把 `rebar`／`rebar_summary` 併入結果。
  2. `_wall_field_rules()` 補 fc′、fy、保護層、懸臂牆身／底板主筋、
     重力／半重力牆面與底部構造筋共 8 欄；`_example_retaining_wall()`
     同步给預設值。
  3. 自動選配（`size: true`）以 `extra_check=_rebar_ok` 篩候選斷面：
     只過穩定但有裂縫 NG 的斷面會被淘汰。
  4. `format_report()` 接上 `rebar_summary`，小於 0.01 的數值改用
     `%.4f`，避免 ρ=0.0020 顯示成 0.00。
- **證據**：
  - 本機 catalog：`wall_stability` 14 個欄位，含 `stem_bar`／
    `base_bar`／`mass_wall_face_bar`／`mass_wall_base_bar`。
  - 線上瀏覽器端 `executeDesignRun('wall_stability', example)`：
    `ok=true`、14 項檢核、配筋 **131.04 kg/m**（2026-11-04 損耗率改 6%
    後；原 12% 版本為 138.46）、牆身 D16@220、
    裂縫 0.243 mm。
  - `design_core_selftest.py` 156 tests OK、工作台自測 0 failure、
    `regression.py` 11 案基準相符。
- **教訓**：新增或修改計算器，不能用「引擎 selftest 全過」結案。
  工作台要驗四個使用者可見面：`CATALOG.field_rules`、`example`、
  `result` 的鍵、`summary` 的文字；線上版再加上「重建＋部署＋瀏覽器
  實跑」一關。**看不到的功能，等於沒有功能。**

## AE. 損耗率分家：把使用者的數值指示自行畫了邊界（2026-11-04，Codex）

- **症狀**：使用者指出「擋土牆鋼筋損耗我從沒說過 12%，我一直都說是 6%」。
  實際程式狀態是：箱涵 6%（`box_culvert.REBAR_LOSS_RATE`），
  擋土牆與排水溝 12%（`rc_design.LAP_ALLOWANCE`）。
- **根因**：箱涵那一輪（§AA.6）依使用者指示把箱涵改成 6% 時，
  為了「不動到 `rc_design.LAP_ALLOWANCE`」而把牆／溝留在 12%，
  還在程式註解寫下「**勿一併改動**」。這把使用者的單一指示
  誤解成「只限箱涵」，等於**替使用者做了未經授權的分家**，
  而且那句註解會變成後續 agent 的免罪金牌。
- **修法**：
  1. `rc_design.LAP_ALLOWANCE` 0.12 → **0.06**；`est_rebar_kg()` 預設
     `extra_ratio` 0.12 → 0.06。牆、溝、涵共用同一常數。
  2. 程式內**硬寫「12%」的字串**全部改為從 `lap_allowance` 動態取值
     （`design_api._wall_rebar_lines`、`case_core` 扶壁／錨定／加勁註記、
     `make_wall_section` 圖說），避免下次改率又漏改。
  3. `qty_models` 的數量 basis 文字、案件 `case.json` 的說明文字、
     回歸基準與四份文件（SOP、產線、斷面圖產線、AGENTS.md）同步更新。
- **前後值（全部 ×1.06/1.12＝0.9464，屬使用者指示的刻意變更）**：

  | 構造物 | 12% | 6% |
  |---|---|---|
  | 懸臂 H=3 m | 138.46 | **131.04** kg/m |
  | 重力 H=3 m | 43.86 | **41.51** kg/m |
  | 半重力 H=4 m | 58.48 | **55.34** kg/m |
  | 扶壁 H=8 m | 621.47 | **588.18** kg/m |
  | 錨定 H=7 m | 326.43 | **308.94** kg/m |
  | 加勁 H=6 m | 51.54 | **48.77** kg/m |
  | 排水溝 U 型 | 24.27 | **22.97** kg/m |

  預算總計同步下降（例：懸臂 447,069 → 440,432 元；排水溝
  662,318 → 656,499 元），箱涵三孔不變（本來就是 6%）。
- **教訓**：**使用者的數值指示是全專案預設，不要替它畫邊界**；
  真要分家必須先問過。常數與註解是「規格」不是「工程判斷」，
  而「勿一併改動」這種註解會把未經授權的落差固化下來——
  寫註解時要註明**依據（誰、何時、為什麼）**。

## AF. 箱涵內角加腋、角隅補強筋與新出圖工具（2026-11-04，Codex）

### AF.1 使用者指出「標準圖的箱涵內角都有倒角」

  沿用**（舊案 `140/210 kg/cm2` 混凝土、「含損耗 5%」）。本輪所有數值

### AF.2 角隅補強筋 = X 形交叉斜筋（角數推導容易錯）

- 做法依標準圖 C110／C111：每內角沿涵長每 200 mm 一組，每組 **2 支
  45° 斜筋**，跨越該角所在牆厚 t，兩端各錨 0.10 m，單支長度 `t√2 + 2×0.10`。
- **角數**：外牆角 4（兩端牆各 2 角，靠土側那面不是內空）
  ＋ 中間牆角 `4(n−1)`（每道中牆 4 角）＝ **4n**。三孔 ＝ 4＋8＝12 角。
  - 常見錯誤：把外牆也算成 4 道牆 → 角數多一倍、鋼筋量多 50%。
- **屬構造筋，不參與構架分析**：構架以矩形剛接斷面計算，對內力保守。
  這是刻意保守假設，必須寫進 docstring 與配筋表 basis，否則後人會以為
  漏算。

### AF.3 `cell_void()` 只畫 2 個加腋角 → 八邊形少 2 點

- 內角加腋後每孔內空是 **8 點八邊形**（上兩角＋下兩角各切 45°）。
  只畫上兩個角時形狀變六邊形，**圖／數對帳的面積對不上**，
  而外框面積與孔洞面積都對，差異只出在內空形狀。
- 教訓：加了任何「挖角」的幾何，**內空多邊形的點數要自己數一遍**，
  不要沿用既有迴圈。

### AF.4 模板量公式要跟著加腋改

```text
舊：2n(B + H)
新：n(2B + 2H − 8c + 4c√2)
```

- 三孔 B=3.00、H=2.50、c=0.20 → **31.594 m²/m**（舊 33.000）。
- **模板會下降**（加腋取代直角面積，斜面 4nc√2 仍小於被取代面積）。

  **本輪引擎自測的模板期望值忘了改，導致 `--selftest` 15/16 FAIL**——
  這是「改了公式沒改對照值」的典型，引擎自測必須跟著重算。

## AH. 建築平面圖照片／藍曬圖向量化與 CAD 轉檔（2026-11-06，三村聯合活動中心 1F/2F 平面圖）

> 完整案例：`d:\Civil_Design_WorkBench\三村聯合活動中心\`
> 產出物：`1F.dwg`、`2F.dwg`
> 參考工具：`d:\Civil_Design_WorkBench\_temp\sancun\build_sancun_cad.py`、`C:\Program\ArtCraft\CADCraft\cadcraft-cli.exe`

### AH.1 雙圖源互補架構（大尺寸圖定骨架，細部藍曬圖定構件）

- **痛點**：舊建物整修工程常同時提供「修繕計畫大尺寸平面圖」與「原建照細部藍曬圖」。修繕圖標註了正確的大跨距尺寸（1220/1230、2570/840、420/380/730/740）、開間、窗牆標註與粉刷施工高度，但常把男女廁所內部、門窗開啟方向省略；而原始藍曬圖繪有完整四扇門、隔間、便器、小便斗、面盆、無障礙扶手與花台，但因翻拍或歷史圖紙造成梯形透視與傾斜。
- **解法**：嚴格按「大尺寸圖數值 → 定結構正交外框與柱網」＋「藍曬圖比例內插 → 定衛浴設備、樓梯踏步與門扇開啟角度」。絕對禁止照歪斜照片描圖，所有非斜角/非圓弧線條一律修正為**絕對水平與垂直**。

### AH.2 臺灣建築平面圖單位慣例（Centimeter vs Meter）

- **痛點**：土木圖（道路、水保、箱涵、整地）慣用「公尺（m，`$INSUNITS=6`）」；但臺灣建築平面施工圖（S=1:100），標註數值（1220、2570、420、330）一律為**公分（cm）**。
- **解法**：建築平面 DWG 繪圖單位採 **1 unit = 1 cm**，DXF 表頭設 `$INSUNITS=5`（Centimeters）與 `$MEASUREMENT=1`（公制 Metric）。
- **標準厚度**：外牆厚度設定為 **25 cm**，室內磚隔間牆設定為 **12 cm**（1/2B 磚牆加粉刷），RC 柱採 50 cm × 50 cm 對角交叉填充線。

### AH.3 Python / ezdxf / Pillow 之工程細節地雷

1. **Pillow 超大圖 `DecompressionBombWarning`**：高解析度掃描圖（如 14028×9920 像素，約 139 MP）直接 `Image.open` 會觸發防 DOS 攻擊警告或中斷。讀圖腳本必須在開檔前宣告 `Image.MAX_IMAGE_PIXELS = None`。
2. **PowerShell 執行 inline Python 的變數展開陷阱**：在 PowerShell 下執行 `python -c "doc.header['$INSUNITS'] = 5"`，PowerShell 會將 `$INSUNITS` 視為環境變數展開成空字串，引發 `DXFKeyError: 'Invalid header variable .'`。一律將 Python 寫為實體腳本放在 `_temp\<案名>\` 下執行（符合 Harness² 規範 1.1）。
3. **ezdxf 圖層線粗（Lineweight）離散值限制**：`ezdxf` 的 `doc.layers.add(..., lineweight=...)` 嚴格要求合法的 AutoCAD 離散線粗整數（如 0, 9, 13, 15, 20, 25, 30, 35, 40, 50... 百分之一公釐），若傳入 `10` 會引發 `DXFValueError: invalid lineweight: 10`。薄線請用 `9` 或 `13`，切勿隨意填整數。
4. **文字與尺寸標註避碰**：中廊或進深較窄處（如 175cm 寬走廊、儲藏室下緣），尺寸標註線與引線 offset 必須置中或調大，防止尺寸字串與隔間牆、門框重疊。

### AH.4 CADCraft CLI 無介面極速轉檔與視覺閉環

- `cadcraft-cli.exe convert input.dxf output.dwg`：0.5 秒內由 DXF 產出合規的原生 AutoCAD 2018 DWG，完全免開 AutoCAD GUI，無 COM 衝突風險。
- `cadcraft-cli.exe convert output.dwg output.png`：支援將 DWG 直接渲染為 PNG 預覽圖，智能體可立即以 `read_file` 進行全圖視覺閉環檢核，確認圖框文字、門窗開向、標註線與圖元完全正常後才交付。

## AI. macOS 環境與圖面缺陷（2026-11-07，Cindy/macOS arm64 首次把本專案跑通）

> 場景：把本專案搬到 macOS（Apple Silicon）上跑。結果 Windows 上「全綠」的產線在 macOS 上
> 三軸全滅，且回歸 11 案 36 項不符。逐一查下去，發現**四個真 bug**（其中三個是圖面缺陷、

### AI.1 macOS 上 `*-cli` 根本不存在（不是「找不到」，是「開 GUI 後就結束」）

- **徵狀**：`/Applications/CADCraft.app/Contents/MacOS/CADCraft convert a.dxf b.dwg`
  會**彈出視窗、印一行版本號、然後結束**，沒有產檔、沒有錯誤訊息、退出碼 0。
  同一支 `GridCraft` 跑 `run --script` 也一樣什麼都沒做。
- **原因**：Windows 版會隨附 headless `*-cli.exe`；**macOS 的 App 套件內只有 GUI 執行檔**。
  執行檔收到未知參數時的行為是「開 GUI 後結束」，所以看起來像成功。
- **解法**：改走 ArtCraft 的 **JSON-lines 控制通道**（`--control <port>` + 逐行 JSON）。
  本專案已內建 `tools/artcraft_cli/`：`cadcraft-cli`／`gridcraft-cli`／`wordcraft-cli` 三支殼層，
  對外維持 Windows CLI 的介面，**呼叫端（`acc.py`／`boq_build.py`／`make_report.py`）不用改**。
  `tools/project_paths.py` 的 `artcraft_cli()` 把它們放在解析順序的最後一段（環境變數 → ARTCRAFT_HOME → PATH → 殼層），
  Windows 仍優先用真正的 `*-cli.exe`。
- **三個 App 的認證不同**（2026-11-07 實測，寫殼層時逐一試出來的）：
  CADCraft = 每個請求 body 帶 `token`；GridCraft = 先送一次 `auth` 握手；
  WordCraft = 每個請求 body 帶 **`key`**（不是 token！），
  憑證檔分別在 `~/.cache/cadcraft-control-<port>.token`、`~/.cache/gridcraft/control-<port>.token`、
  `~/Library/Application Support/WordCraft/control-key.local-<port>`。
- **macOS 版 `saveas` 不接受 `binary:true`**：`binary` 只適用 DXF；DWG 只能 `saveas {path, version:2018}`。

### AI.6 macOS 上 `--install` 把 `.dmg` 當執行檔 symlink 出去 → 假安裝

- **徵狀**：`python tools/project_paths.py --install` 回報「全部備妥」，
  `project_paths.py` 也印 `OpenCADStudio: ~/.local/bin/opencadstudio [OK]`，
  但實際執行 `opencadstudio --version` 噴
  `line 1: xsuT...: command not found`（把二進位當 shell script 解析）。
- **原因**：`tools/install/toolchain.py` 的 `Tool.kind` 對 OpenCADStudio 寫死 `appimage`，
  但 **macOS 的 release 資產是 `.dmg`**（磁碟映像，不是可執行檔）。
  安裝分支走的是「搬檔 + `chmod +x` + symlink」，於是 `~/.local/bin/opencadstudio`
  指向一個 63 MB 的 dmg 檔。**`file` 顯示 `zlib compressed data` 就是徵兆。**
- **解法**（2026-11-08 已修）：
  1. 新增 `_install_macos_dmg()`：`hdiutil attach -nobrowse -readonly` → 複製 `.app` 到
     `/Applications/` → `hdiutil detach` → 回傳 `Contents/MacOS/` 內的真正執行檔。
  2. **掛載點解析要看最後一欄**：`hdiutil attach` 輸出是
     `/dev/disk8s1  <uuid>  /Volumes/Open CAD Studio`（tab 分隔），
     掛載點在**最後一欄**，用「行首是 `/Volumes/`」會永遠找不到（磁碟映像名含空格，必須整段取）。
  3. `_tool_installed()` 與 `project_paths.opencadstudio_exe()` 都補上
     macOS 的 `/Applications/OpenCADStudio.app/Contents/MacOS/OpenCADStudio` 路徑。
  4. `/Applications/` 已有同名 `.app` 時**不覆蓋**，改裝到 `~/.local/opt/` 內的獨立副本。
- **驗收**：`OpenCADStudio --version` 印 `OpenCADStudio 2026.44`；
  `acc.py` 的 `OCS` 指向 `/Applications/.../OpenCADStudio`；
  `ocs_service()` 的 `GET /state` 回 `missing_fonts = []`。
- **教訓**：`--install` 回報「備妥」**不等於**東西真的能用——一定要另外跑一次
  `--version` 實測（本專案的 `_verify()` 已在做這件事，但舊版的 dmg 路徑繞過了它）。

### AI.8 IngeTrazo 的 MCP 橋只收一個客戶端，第二個是「逾時」不是「拒絕」

- **徵狀**：`ingetrazo_check.py --call` 或自建的最小 JSON-RPC 客戶端回
  `Cannot reach IngeTrazo's AI bridge on 127.0.0.1:4763 (Operation timed out)`，
  但 `lsof -nP -iTCP:4763` 明明顯示 **LISTEN**，而且 bridge 的 `_serve()` 也在跑。
- **原因**：IngeTrazo 的橋（`plugins/ai_bridge.py` 的 `_Bridge`）`srv.listen(1)`，
  **一次只接受一個客戶端**。OpenCode 的 MCP 伺服器已經佔住名額時，
  第二個客戶端的 `connect()` 會被 accept 但**不回應**，直到 180 s 逾時。
  `Connection refused` 與 `Operation timed out` 是完全不同的兩件事：
  refused = 橋沒開；**timed out = 橋開著但名額被佔**。
- **解法**：`lsof -nP -iTCP:4763` 找出佔用者 → `kill <那支 ingetrazo-mcp 的 PID>` 釋放名額。
  換 MCP 客戶端前一定要先做這件事。
- **教訓**：多客戶端共存時，「逾時」先查**佔用**再查**服務本身**。

### AI.9 macOS 沒有「輔助取用」權限時，GUI 操作只能靠外掛 API

- **徵狀**：`osascript -e 'tell application "System Events" to ...'` 回
  `osascript不允許輔助取用 (-1728)`，連 `get name of every window` 都失敗。
- **原因**：macOS 對 AppleScript 操控其他 App 要求「輔助取用」授權，
  未授權時**讀取**視窗結構就會被擋，更別說點擊。
- **解法**：IngeTrazo 有官方的**使用者外掛 API**（`core/extensions.py` 的 `user_plugins_dir()`）。
  在 `~/.local/share/ingetrazo/plugins/` 放一個有 `setup(app)` 的外掛，
  呼叫與選單**同一支公開 API**（`window._ai_bridge_section.start()`）自動開橋。
  不需要 GUI 自動化權限，也不改官方檔案。停用＝檔名加 `.disabled`。
- **教訓**：GUI 應用若提供外掛／插件機制，**優先用它**，
  不要為了按一個按鈕去要求使用者開系統權限。

### AI.10 官方 DMG 版的 `.app` 內含多個可執行檔，`project_paths` 別指錯

- **徵狀**：`project_paths.ingetrazo_mcp()` 若指到 `Contents/MacOS/ingetrazo`（主程式），
  MCP 握手會失敗；指到 launcher stub 也一樣。
- **原因**：`.app` 的 `Contents/MacOS/` 內通常有**多個** Mach-O：
  主程式、launcher stub、以及 `*-mcp` 橋接伺服器。**要的是 `ingetrazo-mcp`**。
- **解法**：`project_paths` 的 macOS 分支用 `/Applications/IngeTrazo.app/Contents/MacOS`，
  再由 `ingetrazo_mcp()` 挑檔名為 `ingetrazo-mcp` 的那個；挑不到才退回其餘候選。
- **驗收**：`mcp_probe.py ingetrazo 30 <路徑>` 回 `{"ok": true, "count": 5}`。

### AI.7 macOS `.app` 裡的 launcher stub 不能被 symlink 出去

- **徵狀**：DMG 正確解掛、`.app` 正確複製到 `/Applications/` 後，
  `~/.local/bin/opencadstudio` 若指向 `Contents/MacOS/OpenCADStudio`，
  執行會噴：
  `OpenCADStudio launcher: failed to execute the application: No such file or directory (os error 2)`。
- **原因**：`Contents/MacOS/OpenCADStudio` 只有 665 KB，是 **launcher stub**，
  會回頭找 `.app` 套件內的資源；被 symlink 到別處執行就找不到套件。
  真正的主程式是同目錄的 **`OpenCADStudio-App`（112 MB）**，可獨立執行。
- **解法**（2026-11-08 已修）：
  - `toolchain._macos_app_cli_exe()`：在 `Contents/MacOS/` 內優先挑 `<stem>-App`／`<stem>-app-bin`，
    否則挑**檔案最大的**（launcher stub 通常只有幾百 KB）。
  - `project_paths.opencadstudio_exe()`：macOS 分支同樣回傳 `OpenCADStudio-App`。
  - `--install` 在「已安裝」分支也會補建 `~/.local/bin/<stem>` symlink。
- **驗收**：`~/.local/bin/opencadstudio --version` → `OpenCADStudio 2026.44`；
  `acc.py` 的 `ocs` 後端 `--http` → `/api/v1/ready` 回 200；
  `GET /api/v1/state` → `missing_fonts = []`。

## AJ. 配筋圖主筋與分佈筋繪製規範與對帳器升級（2026-11-08）

### AJ.1 徵狀：工作台生成的配筋圖只有圓點、沒有受力主筋實線

- **徵狀**：使用者指出「設計工作台生成的配筋圖（水溝、擋土牆、箱涵）主筋的位置與設置位置都不對，甚至根本沒有畫出主筋，只有畫出副筋」。
- **原因**：早期程式作者在 `make_wall_section.py` 與 `make_box_section.py` 中誤將「受力主筋間距（如 D16@200）」誤解為「在 2D 橫斷面上排布圓點的間距」，因而通篇僅以 `msp.add_circle()` 繪製浮空圓點，漏掉了沿構件外圍輪廓受彎的連續實線主筋（`LWPOLYLINE`），且對帳器 `dxf_takeoff.py --rebar` 過去僅統計圓點間距，未檢驗實線幾何，導致「假配筋圖」矇混過關。
- **解法**：
  1. **標準圖比對（C048 / C066 / C110）**：
     - **排水溝（D-02）**：受力主筋改為連續 U 型實線（`LWPOLYLINE` on `40_鋼筋`，淨保護層 5 cm），頂端向內涵體方向 90° 彎折 10~12 cm；縱向分佈筋改為貼於 U 型主筋實線『內側』的實心圓點（`CIRCLE` on `40_鋼筋`）。
     - **擋土牆（S-02）**：懸臂式繪製垂直向下彎入基底踵端的受拉 L 型主筋實線（帶向上 90° 彎鉤）、前側受壓 L 型主筋實線、牆頂閉合線、底板頂層受拉筋（帶兩端向下彎鉤）與底板底層筋（帶兩端向上彎鉤）；分佈筋圓點校正貼於主筋線條『內側』；扶壁式、錨定式與加勁式亦補全受拉面垂直與水平主筋實線。
     - **箱涵（S-02）**：頂版與底版繪製連續受力主筋實線（端部向側壁彎折錨定）、外側壁與中壁繪製全高鉛直受力實線，搭配 45° 倒角加腋與角隅補強斜筋；縱向分佈筋排列於各主筋實線『內側』。
  2. **對帳器升級雙軌檢核（`tools/takeoff/dxf_takeoff.py`）**：
     - 新增 `measure_rebar_lines()`：統計 `40_鋼筋` 圖層有效 `LWPOLYLINE` 與 `LINE` 之數量與總長度。
     - 在 `check_rebar()` 中強制檢核：若案件有配筋設計，圖面上主筋實線總長度不得為零且必須 ≥ 0.3 m，否則判定失敗不予交件。
  3. **全案回歸與品管確認**：
     - 11 個案件全案回歸重跑，`baseline.json` 記錄真實分佈筋間距，全案通過。
     - `check_delivery.py` E1~E18 品管檢核全部 0 錯誤可交件。

## AK. OpenCADStudio 切為預設出圖後端（2026-11-10）

### AK.1 徵狀：OCS 出的 PDF 線寬偏離規定，閘門卻全過

- **徵狀**：切換驗證時，用 PyMuPDF 統計同一張 D-02 PDF 的線寬，出現 0.09／0.30 mm（專案規定只有 0.10／0.15／0.20／0.25／0.35／0.40）。中文、版面、黑白都正常。
- **原因**：`acc.ocs_publish()` 傳 `plot_style: "monochrome.ctb"`（名稱）。OCS 的 `plot_styles_folder` 為 `null` 時改讀 `%APPDATA%\OpenCADStudio\plotstyles\monochrome.ctb`，那份檔頭格式與專案 CTB 不同（`ctb.py` 回報 magic 不符）、線寬對照也不同。`check_delivery.py` E18 只看 DXF 內記錄的出圖型式名稱，抓不到。
- **解法**：傳 `tools/acad/plot/monochrome.ctb` 絕對路徑（REST 實測接受絕對路徑）；不需改使用者的 OCS 設定。結果 0.10／0.15／0.20／0.35 mm。
- **預防**：換機器或升級 OCS 後，出圖完用 `pymupdf` 統計 `page.get_drawings()` 的 `width`（pt × 25.4/72 ＝ mm）。

### AK.2 徵狀：成品資料夾出現 `.D-02.dwg.ocs.lock`、`D-02.bak`

- **原因**：`acc.py` 以整組強殺結束 OCS 服務，鎖檔沒機會清；覆寫既有 DWG 時 OCS 自留 `<檔名>.bak`（若原本就有同名 `.bak` 會被 OCS 覆蓋，無法預防）。
- **解法**：`acc._rm_ocs_locks()` 只刪「本次才出現」的鎖檔與 `.bak`。

### AK.3 徵狀：預設切到 OCS 後，解析器仍抓舊版 2026.44

- **原因**：`~/.local/bin/opencadstudio.cmd` 是 `--install` 為舊 portable 產的包裝，排在解析順序前面；MSI 安裝版放在 `Program Files\Open CAD Studio\`（帶空格），且不寫入解除安裝登錄的 `InstallLocation`，無法由登錄取得。
- **解法**：`opencadstudio_exe()` 在 Windows 依環境變數根目錄（`ProgramFiles`、`ProgramW6432`、`ProgramFiles(x86)`、`LOCALAPPDATA`、`LOCALAPPDATA\Programs`）以忽略空格與大小寫的名稱比對尋找；不寫死任何路徑。

### AK.4 澄清：accoreconsole 不是中文基準

本機（AutoCAD 2022 `accoreconsole`）對同一張 D-02 出的 PDF 只有 5 KB、**零文字**（SHX 字型不在其搜尋路徑）。舊文件把它當「中文正確」的基準並不成立；比較中文請用 OCS 或目視。

### AK.5 未驗證項目

Linux／macOS 尚未以新版 OCS 重測。2026-11-08 的亂碼可能與當時 `fonts_folder` 未設或平台有關，**不是**已證實的版本差異（Windows 舊版 2026.44 中文正常）。

## AL. 設計圖（工作台出圖）跑 `check_delivery.py` 的比例陷阱（2026-11-11）

### AL.1 徵狀：設計圖明明沒問題，`check_delivery.py` 卻報 E6／E15 錯誤

- **徵狀**：對工作台產出的設計圖（`SC-1_鋼柱柱腳詳圖.dxf` 等）跑
  `tools/a3_sheet/check_delivery.py <dxf> --scale 600`，得到
  `E6 視口比例 1:20.0（應 1:600）` 與 `E15 字高不符出圖規定…10 處`。
- **原因**：`check_delivery.py` 的 `--scale` 預設 600 是為 **A3 現況平面圖**（1:600）寫的。
  設計圖的比例是各圖自己的（SC-1 是 1:20、B-01 是 1:10、池類 1:200、水面線 1:1000），
  比例不符時 E6 直接報錯，E15 的模型空間字高換算（`字高×1000/比例`）也會跟著算錯。
- **解法**：**比例要從該次出圖的 `_drawing_meta.json` 的 `scale` 欄讀**，不要用預設值：

  ```bash
  s=$(.venv/bin/python -c "import json;print(json.load(open('<out>/_drawing_meta.json'))['scale'])")
  .venv/bin/python tools/a3_sheet/check_delivery.py "<dxf>" --scale $s
  ```

  22 個可出圖計算器以各自比例重跑，E1~E18 錯誤 0 項（只有 W2「建物圖層無圖元」——
  設計圖本來就沒有現況建物，屬預期警告）。
- **預防**：交件閘門的檢核指令一律由 `_drawing_meta.json` 帶比例，不要把 `--scale 600`
  寫死成慣例（`AGENTS.md` §6 的 `--scale 600` 範例只適用於 A3 現況平面圖）。

## AM. 規範查詢台已驗證表格顯示「[object Object]」（2026-11-11）

### AM.1 徵狀

在規範查詢台點《市區道路及附屬工程設計規範_1130912》§7.3.4 →「全文」，
下方「本條已驗證結構化公式／查表」面板的表格內容整片顯示 `[object Object]`。
工程設計工作台的「本次計算引用之已驗證規範公式／表格」也有同樣現象。

### AM.2 原因

已驗證表格的**列**在儲存層有三種形狀（`tools/regs/verified/*.json`）：

| 形狀 | 用途 | 例 |
|---|---|---|
| `{"key": 列名, "values": {欄: 值}}` | lookup（398 張） | `{"key": "設計水深≦60公分", "values": {"最小出水高度(公分)": 15}}` |
| `{"x": 數值, "values": {欄: 值}}` | stepdown（1 張） | `{"x": 0, "values": {"Nc": 5.3, …}}` |
| `[值, 值, …]` | interp（1 張） | `[50, 0]` |

前端（`tools/regs/regs_web.html` 的 `buildVerifiedPanelHtml`）卻假設列是**陣列**：

```js
v.rows.map(r => `<tr>${(Array.isArray(r) ? r : [r]).map(cell => `<td>${esc(cell)}</td>`).join("")}</tr>`)
```

列是物件 → `Array.isArray` 為 false → 被包成 `[r]` → `esc(r)` 走 `String(obj)`
→ 得到字串 `[object Object]`。**不是單一條目的資料壞掉，是全部 400 張表都中招**
（同一段 template 也用在 `tools/design/workbench_web.html` 的 `renderRefTablePreview`）。

### AM.3 解法

1. **資料層正規化**：`tools/regs/verified.py` 新增 `table_grid(x)`，把三種列形狀
   統一成「欄名 + 每列字串陣列」；lookup 表在最左補一欄列名（stepdown 補 `x`），
   清單值以頓號串接、`null` 顯示 `—`。
   `for_clause()`／`references_for()`／`table()` 都多帶一個 `grid` 欄位，
   兩個前端一律優先用 `grid`。
2. **前端 fallback**：`regs_web.html` 加 `verifiedCell()`／`verifiedGrid()`，
   雲端靜態版或舊快取資料沒有 `grid` 時仍能正確渲染。
3. **MCP 輸出**：`verified.format_text()` 整表回覆改用 `grid` 的列陣列，
   代理端不必自己從 `{key, values}` 猜欄位。

### AM.4 預防

新增 `tools/selftest/regs_table_render_selftest.py`（已納入 `run_all.py` 的
`regs-table-render`）：Python 端驗每列欄數與表頭一致、格內無 dict／list；
JS 端真的用 **node 抽出 `regs_web.html` 的 `verifiedGrid()` 跑全部 400 張表**，
輸出不得含 `[object Object]`。沒有 node 時只跳過 JS 段。

### AM.5 連帶修掉的真 bug：catalog 模組漏 import `DesignAPIError`

查上項缺陷時發現 `tools/design/catalog/{_shared,wall,water}.py` 用了
`DesignAPIError` 卻沒有 import它（design_api 會 import catalog.*，反向 import 會循環）。
症狀：任一計算器**缺參數**時，`/api/design/run` 回
`{"error": "NameError: name 'DesignAPIError' is not defined"}`，
前端顯示「計算失敗」而不是「缺少參數 X」。
解法：例外類別定義在 `catalog/_shared.py`，`design_api.py` 改為
`from catalog._shared import DesignAPIError`（同一個類別物件，外部取用不變）。
守門：`design_workbench_selftest.py` 驗「缺參數的回覆不含 NameError」且
「`design_api.DesignAPIError is catalog._shared.DesignAPIError`」。

## AN. 規範入庫只 commit 已驗證條目，乾淨 checkout 的 `regs-verified` 必紅（2026-11-14）

### AN.1 徵狀

`tools/regs/verified/*.json` 加了新規範的條目（例如 `sewer105_*`、`swc_tech_c`），
工作區 `run_all.py --no-cad` 全綠；但在 `git worktree add --detach _temp/cleancheck HEAD`
的乾淨 checkout 重跑，`regs-verified` 以大量
`FAIL lint sewer105_t1_1_peaking_factor: 規範代號 sewer105 不在索引` 失敗。

### AN.2 原因

已驗證條目只記 `src`／`clause`，真正被查的是 `data/法規/_regs_index.sqlite` 的
`src` 表。新來源是在本機 `fetch_regs.py` → `build_index.py` 之後才進索引，
但入庫 commit 只提交了 verified json 與 manifest，**來源全文檔與重建後的索引沒進版控**，
乾淨 checkout 仍拿到舊索引（少 5 部來源）。

### AN.3 解法

同一筆入庫工作要一起提交三件東西：

1. `data/法規/<來源>_全文.txt` 與 `_全文_NFKC.txt`（`build_index.py` 只讀 `_全文.txt`，
   NFKC 版缺了會自動生成，但一併提交可避免每台機器重建差異）；
2. 該來源的原始檔（如 pcc_spec 的 314 章 odt/doc/docx、src100 各章 PDF）；
3. 重建後的 `data/法規/_regs_index.sqlite`。

原始 PDF 僅供存檔與追溯，不影響索引重建，可不入庫（manifest 已記網址與雜湊）。

### AN.4 預防

收工 SOP §4.1 的乾淨 checkout 驗收要**連 `run_all.py --no-cad` 一起跑**，
不能只跑 `regression.py`——回歸只看 cases，看不到規範庫的索引落差。
CI（`.github/workflows/selftest.yml`）不會發現這件事，因為索引是版控內的二進位檔，
CI 拿到的是上一次提交的版本。

### AN.5 連帶確認

`_regs_manifest.json` 是追蹤檔，但 `files.text` 指到的全文檔若不在版控內，
新機器只能靠 `fetch_regs.py` 重新下載；本次已把 4 部新來源的全文與原始檔補入，
索引來源數 38 → 43。
