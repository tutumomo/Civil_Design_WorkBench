# 工程預算書產線（tools\boq）

> 2026-10-28 建立｜適用：土木小型工程（道路、排水溝、擋土牆、邊坡）之施工預算書
> 為「設計圖／預算書／設計報告」三大交付中的**預算書**產線

---

## 1. 一句話

**輸入一份案件 JSON（工項＋數量＋單價或單價分析），輸出一份跟公司現有格式一致的 5 工作表預算書 `.xlsx` ＋ `.pdf`，費率層全部是活公式，並自我驗證總計。**

已用公司真實案件（`103.崙背鄉草湖村河川便道改善工程`）逆向驗證：**12 個費率值 + 6 個品項 + 總計 882,434 元逐項完全一致**。

---

## 2. 快速用法

```bat
set PYTHONIOENCODING=utf-8

:: 1) 產生預算書（xlsx + pdf + 計算書 json + 指令 jsonl）
python <專案根目錄>\tools\boq\boq_build.py ^
  <專案根目錄>\tools\boq\examples\AC刨鋪5cm工程.json ^
  --out-dir <專案根目錄>\AC刨鋪5cm工程\預算書

:: 2) 只產指令碼不執行（先檢查排版指令）
... boq_build.py <案件.json> --out-dir <dir> --dry-run

:: 3) 不產 PDF
... boq_build.py <案件.json> --out-dir <dir> --no-pdf

:: 4) 費率核心回歸測試（改公式後必跑）
python <專案根目錄>\tools\boq\selftest\selftest_rules.py
```

退出碼：`0` = 產生成功**且** xlsx 回讀總計與 Python 計算一致**且** `gridcraft-cli check` 通過；非 0 不可交件。

### 檔案結構

| 檔案 | 角色 |
|---|---|
| `boq_rules.py` | **計算核心**：費率模型、Excel ROUND 語意、單價分析基準（basis）。純函式，無 I/O |
| `boq_build.py` | **排版與執行**：案卷 JSON → GridCraft 指令 → xlsx/pdf → 回讀驗證 |
| `prices\營建物價_11405_路面工程_中部.json` | 單價資料庫（來源：`D:\公司案件\20250619 營建物價查詢\路面工程.pdf`，中部價） |
| `selftest\` | 回歸測試（真實預算書逆向還原的輸入） |
| `examples\AC刨鋪5cm工程.json` | 示範案（數量取自已交付的 A3 平面圖實測值） |

### 產出檔（`<工程名稱>_預算書.*`）

| 檔 | 內容 |
|---|---|
| `.xlsx` | 5 工作表：封面／總表／詳細表／單價分析表／數量計算 |
| `.pdf` | 上述 5 表全部頁面，A4（封面直式、其餘橫式），自動縮放一頁寬 |
| `_計算書.json` | 逐項單價/複價與 12 個費率中間值 —— **稽核用，數字有爭議時看這支** |
| `_指令.jsonl` | 實際送給 GridCraft 的 250~400 條指令（可重跑、可 diff、可手改） |

## 3. 案件 JSON 格式

```jsonc
{
  "project": "工程名稱",
  "location": "施工地點",
  "agency": "主辦機關（會印在封面與表頭）",
  "date": "115年1月",
  "code": "工程案號（可空）",
  "rates": { "adj_profit": 0, "adj_air": 0 },   // 可省略，見 §5
  "items": [
    {
      "no": "01",                  // 項次；純數字會自動保持 01 不被轉成 1
      "name": "工項名稱",
      "unit": "M2",                // 計價單位
      "qty": 850.6,                // 數量
      "calc": "160.84*5.29",       // 數量計算式（印在「數量計算」表，可追溯來源）
      "note": "0296140032 中部",    // 印在「編碼(備註)」欄，寫單價來源或規範依據

      // 以下二選一：
      "price": 75.0,               // (A) 直接給單價
      "analysis": [                // (B) 給單價分析（工料明細），單價由合計推算
        { "name": "開挖機", "unit": "日", "qty": 0.75, "price": 9000, "note": "" }
      ],
      "basis": 100                  // (B) 專用：單價分析基準數量，見 §5
    }
  ]
}
```

**單價採 (B) 優先**：給了 `analysis` 就自動產生「單價分析表」區塊，詳細表的單價用公式引用它 —— 這是公司預算書的既有習慣，也讓「單價怎麼來的」可稽核。

---

## 4. 五個工作表

| 表 | 內容 | 誰填 |
|---|---|---|
| **封面** | 工程名稱、施工地點、編製日期、工程編號、抬頭「施工預算書」、技師簽署欄、主辦機關 | 自動 |
| **總表** | 壹 發包工程費（6 項）＋貳 間接工程費（3 項）＋總計 | 全自動（費率公式，引用詳細表） |
| **詳細表** | 逐項 項次/項目/單位/數量/單價/複價/編碼，接費率層與總計 | 工項自動；**費率層公式自動** |
| **單價分析表** | 每個有 `analysis` 的工項一個區塊：工料名稱/單位/數量/單價/複價 → 合計 → 每單位單價 | 全自動 |
| **數量計算** | 編號/項目/計算式/＝/數量/單位 | 自動（`calc` 欄直出） |

## 5. 費率模型（已與真實預算書對帳）

| 項 | 公式 | 參考案值（A=690,800） |
|---|---|---|
| 小計A（直接工程費） | Σ(數量×單價) | 690,800 |
| 二 工程品質管制費 | `ROUND(A×0.6%, -1)` | 4,140 |
| 三 職業安全衛生管理費 | `ROUND(A×0.5%, -1)` | 3,450 |
| 四 營造綜合保險費 | `ROUND(A×0.6%, -1)` | 4,140 |
| 五 承包商利潤及管理費 | `ROUND(A×7%, 0)` ＋`adj_profit` | 47,851（adj = **−505**） |
| 六 營業稅 | `ROUND((A+二+三+四+五)×5%, 0)` | 37,519 |
| 壹 發包工程費 | A＋二…六 | 787,900 |
| 貳.一 主辦機關工程管理費 | `ROUND((壹−六−四)×3.5%, 0)` | 26,118 |
| 貳.二 空氣污染防制費 | `ROUND(壹×0.3%, 0)` ＋`adj_air` | 2,418（adj = **+54**） |
| 貳.三 設計監造費 | `ROUND((壹−六−五−四)×10.5%×0.9, 0)` | 65,998 |
| 間接工程費小計 | 貳.一＋貳.二＋貳.三 | 94,534 |
| **總計** | 壹＋間接 | **882,434** |

### 兩個必須知道的事

1. **`adj_profit` / `adj_air`**：真實預算書的利潤是「7% 後再 −505」、空污是「0.3% 後再 +54」——這是**人工微調**（讓總計好談、或對齊機關習慣）。本工具照實支援，預設 0。**不是 bug。**
2. **`basis`（單價分析基準）**：單價分析表的「單位：100 M2」代表工料數量是「每 100 M²」的用量，合計 30,000 → 每 M² 單價 = 30,000 ÷ 100 = **300**。參考案 04／05 兩項即為 `basis: 100`，其餘為 1。**漏了 basis，單價會大 100 倍。**

### 預算書編列微調原則：可微調項與方向（2026-10-28 使用者指定，必須遵守）

編列預算書時**有兩項會刻意偏離標稱費率，用來把總計調到目標金額**。這是正常作業，**不是錯誤**：

| 項目 | 標稱費率 | 可微調方向 | 原因 |
|---|---|---|---|
| **包商利潤及管理費** | 小計A × 7%（或 8%） | **一律用扣的**（實際 ≤ 標稱值） | 怕被質疑圖利廠商，所以只能往下調 |
| **空氣污染防制費** | 發包工程費 × 0.3% | **只加不減**（實際 ≥ 標稱值） | 空污費屬規費性質，多編不構成圖利 |

**稽核與判讀準則：**
- 看到「利潤 ≠ 小計A×7%」→ **先確認是不是向下微調，不要直接判定計算錯誤**。
- 看到「空污費 ≠ 發包工程費×0.3%」→ **先確認是不是向上微調，不要直接判定計算錯誤**。
- 看到「總計剛好是整數（3,000,000／4,760,000）」→ **這是上述兩項微調的結果，不是回填造假**。

**實測驗證（兩案四項全部符合此規則）**：

| 案件 | 利潤 實際 vs 7% | 空污 實際 vs 0.3% |
|---|---|---|
| 崙背中厝 | 257,085 vs 257,087（**−2，扣**）| 13,617 vs 12,899（**+718，加**）|
| 崙背羅厝 | 160,528 vs 161,534（**−1,006，扣**）| 8,402 vs 8,016（**+386，加**）|

其他費率層（品質管制費、職安費、保險、營業稅、工程管理費、設計監造費）**沒有**這種微調慣例，若與標稱費率不符才需要問依據。

### 捨入規則

一律採 **Excel ROUND 語意（四捨五入、進位遠離零）**，由 `boq_rules.xround()` 實作。
**不可改用 Python 內建 `round()`**（銀行家捨入，`.5` 會進到偶數，與 Excel 不同）。

## 6. 單價資料庫

`prices\營建物價_11405_路面工程_中部.json` —— 8 筆路面工程資源代碼（刨除／黏層／透層／密級配／底層粗級配／級配底層／回填），含北中南東四區價格。

**用法**：在案件 JSON 的 `note` 欄寫資源代碼（如 `0296140032 中部`），單價填資料庫對應值。這樣「這個單價從哪來」有據可查，也方便日後換版。

> 目前只有路面工程一頁。要擴充（排水／擋土牆／結構／標線／交維），把對應的營建物價 PDF 放進 `D:\公司案件\20250619 營建物價查詢\`，照同一格式加進 `prices\`。

## 7. 驗證方式

```bat
:: 費率核心（不啟動任何 GUI／工具，秒級）
C:\Python312\python.exe tools\boq\selftest\selftest_rules.py

:: 產出後的兩道自動檢查（boq_build.py 內建，不需另跑）
::   ① 回讀 xlsx 的 詳細表!F{總計列}，必須等於 Python 算出的 total
::   ② gridcraft-cli check：公式重算一致性 + xlsx round-trip
```

**交件前人工檢查（工具做不到的）**：
1. 開 PDF 目視：封面機關名稱、日期、工項名稱有沒有錯字
2. 數量對得回圖面（`calc` 欄要能追到 DXF 實測值或數量計算）
3. 單價與當期詢價/物價是否相符（`note` 欄的資源代碼對不對）
4. 標線、交通維持這類「假設值」工項已換成正式詢價

## 8. 已知限制（誠實清單）

| 限制 | 影響 | 目前處置 |
|---|---|---|
| 只有路面工程單價庫（8 筆） | 排水／擋土牆／結構工項要自己填單價 | `note` 標「假設值，須詢價」 |
| 沒有「預算書→投標文件」轉換 | 投標須知、詳細價目表 PDF 格式另做 | 未做 |
| 沒有工程數量自動取用 DXF | 數量要人工從圖面量測值填進 JSON | 下一步：接 `check_delivery` 的圖層量測 |
| Excel 版面非 100% 等同人工排版 | 欄寬、跨頁切割需人工微調 | 已設 A4 自動縮放、列高與框線；仍建議開 Excel 目視一次 |
| 無「單價分析表」的資源代碼自動填入 | 工料名稱要自己打 | 可從 `prices\` 擴充查表 |
| 沒有預算書版本比較 | 改版前後差異要自己 diff | 可 diff `_計算書.json` |

## 9. 與其他產線的接合

```
圖：site_basemap.py → make_sheet.py --publish → acc.py → check_delivery.py
                                 ↓ (數量：L/A/V 實測值)
預算：boq_build.py ← 案件 JSON（qty 來自上一步）＋ prices\ 單價庫 → 預算書 xlsx/pdf
                                 ↓ (工項與數量)
報告：tools\report\（見 docs\設計報告產線.md）
```

三大交付的共同資料源應該只有一份「案件 JSON」—— 圖面量測值填進來，預算書與設計報告都吃它，避免三處各寫一次而互相矛盾。
